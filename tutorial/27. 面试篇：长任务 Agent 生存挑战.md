# 04｜长任务 Agent 生存挑战：从一次回答到持续交付

> 本篇讨论 Memory、Skills、Checkpoint、DeepAgent、结构化输出与 Artifact，重点是长任务 Agent 如何保存上下文、复用方法、恢复执行并交付可持续使用的产物。

每一关先用 30 秒给出自己的判断，再看问题和参考回答。回答时可以重点检查三件事：状态存在哪里、失败后如何恢复、成本如何控制。

</aside>

## 故事背景：从一次回答到持续交付

你接手了一个只能进行单轮问答的助手。随着任务逐渐变长，它开始需要处理跨会话记忆、多步调研和报告生成，也随之暴露出记忆污染、上下文膨胀、任务中断、版本不兼容和预算超限等问题。

目标是建立一套可记忆、可恢复、可审计、可交付的执行链路，而不是不断加长 Prompt。

### 通关规则

- 看到「轮到你决策」时先暂停，尝试口述答案。
- 给出方案的同时，说明适用边界和可能的失败方式。
- 能说出概念分类只是基础；能处理污染、迁移、中止和交付，才接近生产要求。

## 第 1 关：完整对话历史拖垮了 Prompt

### 事故现场

多轮对话后，你把全部历史直接拼回 Prompt。token 消耗持续上升，已经结束的旧话题也开始干扰当前任务。

### 轮到你决策

Memory 可以分成哪些类型？为什么不应该无限追加历史？

### 面试官问题

Agent 的 Memory 有哪些类型？为什么不能一直把历史塞进 Prompt？

**参考回答**

常见记忆可以分为五类。分类的意义在于，它们使用的存储介质、生命周期和权限边界并不相同。

| 类型 | 存储位置 | 生命周期 | 典型内容 |
| --- | --- | --- | --- |
| 短期记忆 | 上下文窗口 | 单次会话 | 最近 N 轮消息、滑动窗口 |
| 长期记忆 | 向量库 / KV | 跨会话持久保存 | 用户偏好、稳定事实、长期背景 |
| 任务状态 | Checkpointer | 任务生命周期 | 执行位置、中间结果、待处理步骤 |
| 外部知识 | 文档库 / 检索索引 | 按需检索 | RAG 文档和业务资料 |
| 反思记忆 | 独立记忆库 | 长期积累 | 失败原因、修正策略、经验总结 |

完整追加历史的问题不只是成本高。每轮都重新输入此前内容，token 消耗会快速增长；上下文过长还容易出现 lost-in-the-middle，模型对关键信息的注意力被稀释。历史中也可能包含与当前任务无关、甚至不应继续暴露的敏感信息。

更合适的做法是按用途分开处理：最近几轮用于保持指代连续；长期背景保存为摘要；稳定事实使用结构化存储并按需召回；任务进度写入 checkpoint；业务知识交给 RAG。

**要点**

> Memory 设计关注的不是保存得多不多，而是信息是否以合适的粒度放在了合适的位置。
>

## 第 2 关：错误记忆持续影响后续回答

### 事故现场

系统把用户偏好写反了，长期记忆中留下了错误的「喜欢简洁回答」。此后每次召回这条记录，Agent 都会继续沿着错误方向生成内容。

### 轮到你决策

记忆系统需要处理写入、检索、更新和遗忘。你会如何降低污染风险？

### 面试官问题

工程上如何决定记忆的写入、检索与更新？如何防止记忆污染？

**参考回答**

记忆工程可以拆成一套完整的读写与更新流程：

- **写入内容与时机**：只提取值得长期保存的事实、偏好、关系和结论，不逐字保存整段对话。写入可以走热路径，即在对话中同步抽取，优点是及时，代价是增加延迟；也可以离线批处理，降低在线延迟，但会出现短暂的一致性窗口。
- **检索方式**：不能只看语义相似度。Generative Agents 的经典方法会综合相关性、时效性和重要性；生产系统通常采用向量检索、时间衰减和重要性加权的混合排序。
- **更新与冲突处理**：可以为事实增加 `valid_from / valid_to`，让新事实使旧事实失效，而不是直接覆盖。这样既能避免同时召回冲突信息，也保留了可追溯记录。
- **遗忘机制**：通过 TTL、重要性衰减和显式删除控制记忆规模，并满足合规删除要求。
- **污染防护**：写入前校验；每条记忆记录来源、置信度和有效期；召回时降低过期或低置信内容的权重。出现 bad case 后，应能追踪是哪条记忆影响了结果。

Mem0 提供自动提取与冲突处理能力；Zep 使用时序知识图谱描述事实的变化；LangMem 区分语义、情景和程序记忆。这些方案本质上都在处理同一组问题：存什么、何时存、如何取、如何更新。

**要点**

> 把历史保存下来只是第一步。生产级记忆还需要抽取、排序、更新、遗忘和纠错机制。
>

## 第 3 关：重复写了十遍的分析方法

### 事故现场

每次做需求分析时，你都会临时在 Prompt 中补上一段方法：从功能、安全、风险和验收等维度展开。写了很多次，内容却始终不完全一致。

### 轮到你决策

这类可复用方法适合沉淀成什么？它与 Prompt、RAG、Tools 有什么区别？

### 面试官问题

Skills 是什么？它和 Prompt、RAG、Tools 有什么区别？如何注入 Agent？

**参考回答**

Skills 是可复用的程序性知识，用来描述某类任务应该如何完成。它适合承载团队已经验证过的方法、步骤、清单和模板，避免每次在 Prompt 中重新编写。

| 概念 | 主要作用 |
| --- | --- |
| Prompt | 说明当前任务及其约束 |
| RAG | 提供业务事实和外部知识 |
| Tools | 提供查询、计算或执行能力 |
| Skills | 提供完成某类任务的方法 |

在记忆的类比中，RAG 更接近语义记忆，即知道相关事实；Skill 更接近程序记忆，即知道具体做法。

Skill 的注入通常采用渐进式披露：启动时只放入每个 Skill 的名称和简介；确定任务匹配后，再加载完整的 `SKILL.md`；只有确实需要时，才继续读取其中引用的脚本、模板和资源。这样可以保留较大的 Skill 库，又不必一次把全部内容放入上下文。

常见注入方式包括：

- 启动时全量加载：实现简单，但容易增加 token 消耗并干扰选择。
- 按任务路由：上下文占用较低，但依赖路由准确率。
- 作为子 Agent 能力封装：隔离性较好，但会增加编排复杂度。

Skill 应纳入版本管理，变更前通过评估，必要时支持灰度和回滚。Skill 可以包含脚本或操作清单，但仍需遵守系统原有的权限与审批规则。

**要点**

> RAG 负责提供事实，Tools 负责执行动作，Skills 负责沉淀做事方法。Skill 的价值来自复用和治理，而不是数量。
>

## 第 4 关：任务中断后遇上版本升级

### 事故现场

一个运行了几十分钟的任务在中途遇到服务重启，内存状态全部丢失。恢复服务时，代码和 Prompt 已经发布了新版本，旧 checkpoint 也无法直接反序列化。

### 轮到你决策

为什么长任务需要 checkpoint？版本升级后，旧任务如何安全恢复？

### 面试官问题

Checkpoint 有什么作用？长任务运行期间发布新版本，旧 checkpoint 还能恢复吗？

**参考回答**

Checkpoint 用来保存执行状态，使任务能够中断、恢复、回放和审计。设计时要明确保存内容、写入粒度和存储位置。

- **保存内容**：会话消息、工具调用及结果、图节点或状态机位置、待审批操作、循环次数和预算计数器。
- **写入粒度**：可以在每个节点或 super-step 完成后写入。LangGraph 采用这种模型，因此可以回到某个 checkpoint 分叉重跑；同一任务通过 `thread_id` 串联状态。
- **存储位置**：演示环境可以使用 MemorySaver；生产环境通常需要 SqliteSaver、PostgresSaver、Redis 等持久化方案。

生产环境还需要处理序列化、状态 schema 版本、并发恢复、数据清理和访问权限。例如两个 worker 同时恢复一个 thread 时，需要加锁或使用乐观并发；checkpoint 长期累积时，需要设置 TTL 或归档策略。

版本升级后的恢复通常采用以下策略：

1. 已开始运行的任务固定使用启动时的代码、Prompt 和 Skill 版本，新任务再切换到新版本。
2. 状态中记录 schema 和运行版本，恢复时先进行兼容性校验。
3. 版本不兼容时执行迁移脚本；无法可靠迁移则安全失败并告警，避免带着错位状态继续执行。

**要点**

> Checkpoint 不只是保存进度。生产实现还要解决版本兼容、并发、清理、权限和失败恢复。
>

## 第 5 关：反思循环没有停止

### 事故现场

一个调研任务不断重复「反思—调用工具—再次反思」，迟迟没有收敛，最终耗尽 token 预算。

### 轮到你决策

哪些任务适合使用 DeepAgent？如何限制循环和预算？

### 面试官问题

什么是长链任务？为什么需要 DeepAgent？如何避免无限循环与预算失控？

**参考回答**

长链任务通常包含较多步骤、较长执行时间、多轮工具调用和跨阶段上下文，例如生成完整调研报告，或从需求分析一直执行到修改代码并创建 PR。

DeepAgent（例如 deepagents）可以理解为一套面向长任务的 Agent Harness。它通常提供以下能力：

1. **显式规划**：使用 planning 或 todo 工具记录计划，降低执行过程中遗忘目标的概率。
2. **子 Agent 委派**：各子 Agent 使用独立上下文，主 Agent 只接收必要摘要，减少不同子任务之间的干扰。
3. **虚拟文件系统**：将较大的中间产物写入文件，在上下文中保留引用，避免历史不断膨胀。
4. **长期上下文管理**：结合更完整的系统约束，对任务状态和信息流进行管理。

固定 workflow 的执行路径更明确，通常更容易测试和审计；DeepAgent 能动态规划，适应性更强，但测试、成本控制和行为审计也更困难。

防止循环不能只依赖 Prompt，需要在运行时设置硬约束，包括最大迭代次数、工具调用次数、执行时长和 token 预算；还可以检测重复动作，并在同类错误连续出现时中止。Critic 可以参与判断是否已达到停止条件，但它本身也需要预算限制。

反思循环的成本会快速增加，因为每一轮通常都要重新输入工具定义和历史记录。达到上限时，系统应保存 checkpoint，返回当前可用的部分结果，并标记后续恢复所需的信息。

**要点**

> 长任务需要明确的运行时边界。达到限制后，系统应保留进度并给出可用结果，而不是继续无上限重试。
>

## 第 6 关：Markdown 很好看，但下游无法解析

### 事故现场

Agent 生成了一段排版完整的 Markdown 需求分析。前端希望渲染成卡片，后端希望存入字段，评估系统还要逐项打分，但这段文本没有稳定的数据结构。

### 轮到你决策

结构化输出解决了什么问题？工程上如何保证输出符合约定？

### 面试官问题

为什么 Agent 系统需要结构化输出？工程上如何保证？

**参考回答**

Markdown 适合阅读，但不适合作为系统间的稳定接口。将需求分析拆成 `title`、`summary`、`userStories`、`risks`、`acceptanceCriteria` 和 `priority` 等字段后，前端可以渲染，后端可以存储，评估程序可以逐项评分，工作流也能继续处理。

常见保证方式从弱到强包括：

- **Prompt 要求返回 JSON**：实现简单，但模型可能添加解释文字或代码围栏。
- **JSON mode / response_format**：可以保证输出是合法 JSON，但不一定符合业务 schema。
- **Function calling / tool schema**：按参数 schema 生成，稳定性更高。
- **约束解码（constrained decoding / grammar / strict）**：在解码阶段排除不符合语法的 token，可以严格满足 schema。约束过强可能影响推理，因此可以先完成自由推理，再生成结构化结果，或在 schema 中保留适当的推理字段。
- **业务校验与重试**：使用 Pydantic 或 zod 验证类型和业务规则；失败时把错误信息反馈给模型，让它修正后重试。

流式输出还可以使用 partial JSON 解析，实现边生成边渲染。使用枚举和联合类型前，需要确认所用解码器的支持情况。

**要点**

> 结构化输出的目标，是让结果能够被展示、存储、评估和继续处理，而不只是在聊天窗口中便于阅读。
>

## 第 7 关：用户需要的是报告文件，而不是长消息

### 事故现场

用户要求一份竞品调研，Agent 在聊天中返回了三千字。用户随后想保存、修改和转发给同事评审，却没有一个独立产物可以继续使用。

### 轮到你决策

用户需要的最终结果是什么？如何把问答能力扩展为交付能力？

### 面试官问题

什么是 Artifact？如何把只会回答的 Agent 升级为能够交付结果的 Agent？

**参考回答**

Artifact 是 Agent 产生的可持续使用的结构化产物，例如报告、代码、表格、测试计划或 PR 草稿。它有独立身份和版本，可以被保存、修改、比较、引用和协作，也可以进入后续流程。

聊天消息通常是线性的交互记录；Artifact 则是对话之外的持久状态。要从回答问题扩展到交付结果，系统通常需要补齐以下能力：

- 任务建模：拆分步骤、状态和预期产物。
- 工具接入：允许 Agent 查询信息并执行必要动作。
- 状态管理：使用 checkpoint 保存执行进度。
- 权限与审批：对高风险或有副作用的操作设置边界。
- 行为验证：检查产物是否真正满足要求。
- 结果持久化：为产物提供独立存储和版本。
- 失败恢复：任务中断后能够继续或安全结束。

行为验证经常被忽略。代码应运行测试，报告应通过清单或评估标准。仅仅生成了一个看起来完整的结果，并不能证明任务已经完成。

**要点**

> Chat 适合交互，Artifact 适合交付。后者还需要状态、权限、验证、持久化和恢复能力。
>

## 高阶追问（Staff 级）

> 掌握概念分类之后，还需要继续考虑数据删除和运行复现。
> 

### A1. 被遗忘权：记忆分散在多个系统中，如何完整删除？

- 用户数据可能同时存在于向量库、checkpoint、trace 日志、缓存、派生摘要和 embedding 中，只删除主库并不完整。
- 可以让 `user_id` 贯穿所有存储，再通过统一的删除编排执行级联清理，同时写入 tombstone 和删除审计。
- 日志与备份需要明确留存周期，并与 GDPR 等合规要求对齐。
- 备份难以逐条修改时，可以采用 crypto-shredding：使用每用户密钥加密数据，删除密钥后使对应数据无法恢复。
- 进一步追问：删除原文是否足够？不够，向量和派生摘要也需要删除。备份中的副本则要通过到期窗口和后续清理处理。

### A2. Skill 版本化与可复现：线上效果下降时，如何定位使用过的 Skill？

- Skill 应纳入 Git 并设置版本号，必要时记录校验 hash，防止内容被静默修改。
- 运行 trace 需要记录本次注入的 Skill 及其版本，才能把质量变化定位到具体变更并执行回滚。
- Skill 变更应经过评估门禁，并支持灰度和回滚；内容过长时，只按任务需要加载相关部分。
- Skill 可以包含工具调用脚本或操作清单，但不能绕过权限与审批。多个 Skill 冲突时，需要通过任务路由和优先级规则进行裁决。

每项 0～2 分，总分 10 分：

| 评分项 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 记忆工程 | 只会追加历史 | 能区分记忆类型 | 能说明抽取、检索、更新和污染治理 |
| Skills 治理 | 每次临时写 Prompt | 知道沉淀复用方法 | 能处理任务路由、版本和权限边界 |
| 长任务状态 | 状态只保存在内存 | 会使用 checkpoint | 能处理迁移、恢复和安全失败 |
| 结构化与交付 | 只输出 Markdown | 知道需要结构化 | 使用 schema 约束、校验和 Artifact |
| 预算与恢复 | 只依赖 Prompt 停止 | 设置最大迭代或超时 | 设置预算门槛，并支持中止、审计和续跑 |

### 60 秒终局口述

> 如果要把一个问答型 Agent 升级为能够持续交付的系统，你会如何管理记忆、沉淀 Skill、保存长任务状态，并确保任务在中断、版本发布和预算超限时仍能保留有效工作？
> 

回答至少覆盖：记忆分层与更新、Skill 路由与版本、checkpoint 与迁移、结构化输出、预算中止和 Artifact 交付。

## 本篇小结

这一套能力可以串成下面的链路：

```
Memory 保存必要上下文
→ Skills 复用任务方法
→ Checkpoint 记录长任务状态
→ DeepAgent 负责规划与委派
→ Structured Output 让结果可被系统消费
→ Artifact 保存最终产物
```

长任务 Agent 的核心不在于使用更长的 Prompt，而在于是否具备可恢复、可审计、可控预算和可验证的状态管理。最终交付也不应停留在一段聊天回复，而应成为可以保存、编辑、评估和继续流转的产物。
