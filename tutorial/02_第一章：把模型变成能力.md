如果说上一章讨论的是开发范式为何会改变，那么从这一章开始，我们正式进入实践层面：一款智能体究竟应该如何着手开发。

在动手之前，需要先想清楚一个问题：当我们谈“开发智能体”时，究竟是在开发什么？是一个会聊天的模型、一个能执行任务的流程，还是一种能够接入系统并持续运行的工程化能力？

本章先不急着讨论复杂 Agent 设计，而是回到最基础的一层：模型调用。因为后续所有能力——工作流、工具调用、检索增强、多智能体协作——最终都建立在这一层之上。

本章重点解决五个问题：

- 如何定义角色与任务
- 如何组织上下文
- 如何约束输出
- 如何让模型结果被程序稳定接住
- 如何把一次调用封装成可复用模块

> 注：本书示例均基于 Node.js 技术栈，示例所用接口由超哥的 [Amux](https://link.juejin.cn/?target=https%3A%2F%2Fapi.amux.ai) 友情赞助。

## 1.1 起点：为什么要从模型调用开始

很多人在初学智能体开发时，会把注意力放在更显眼的部分：工具调用、任务编排、多轮执行、自动检索，甚至多智能体分工。

这些能力当然重要，但它们不是起点，而是建立在模型调用之上的扩展。

如果模型输入设计不清晰、输出结果不稳定、返回格式不可控，那么后续叠加的每一层能力，都会放大这种不确定性：工作流会放大错误，工具链会扩散偏差，自动化执行会把局部问题带进整个系统。

这也是智能体开发和普通“用一下模型”的区别。前者关心的不是模型能不能偶尔给出一个不错的回答，而是它能否在系统里稳定工作。

换句话说，开发者需要的不是一次“看起来很聪明”的生成，而是一种可约束、可复用、可验证的能力。

从工程角度看，这一步至少包含三件事：

1. 明确模型调用的基本结构
2. 降低输出漂移
3. 让结果能够被程序解析与消费

只有把这三件事处理清楚，模型才算真正从只会生成文本的通用模型，变成可以进入系统的软件模块。

**模型调用不是智能体开发之前的准备动作，而是智能体开发本身的起点。**

## 1.2 调用：一次受约束的对话

![Gemini_Generated_Image_w38544w38544w385.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/bef50cd6edf24366b9b910ccd85a8691~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2816&h=1536&s=7214268&e=png&b=e8d8bd)

当我们说“调用一次大模型”时，很多人的第一反应是：发一句话，等待模型返回一段回答。

从使用者视角看，这种理解没问题。但进入开发视角后，一次模型调用就不只是“问一个问题”，而是在设计一次带有目标、角色边界、上下文信息和输出约束的受控交互。

**调用模型的本质，不是把一句话交给 AI，而是在设计一次受约束的对话。**

模型输出质量的上限，往往取决于你如何组织这次调用，而不仅仅取决于模型本身有多强。

### **1.2.1 从“问答”到“受约束的对话”**

如果只是把模型当作聊天对象，一次调用可以很随意：

- “帮我分析一下这个需求”
- “帮我写个函数”
- “帮我看看这个功能怎么做”

这类方式适合低风险、探索式场景。但智能体系统不接受“差不多就行”。

一旦模型输出要进入工具调用、任务编排、状态更新或后续代码处理，开发者关注的就不只是“能不能答出来”，而是：

- 输入是否表达清楚
- 模型是否理解角色
- 上下文是否足够
- 输出格式是否可控
- 结果能否交给后续代码处理
- 相似输入下是否会严重漂移

当模型进入软件系统，它就不再只是一个对话界面，而是一个需要被设计、约束和验证的系统组件。

### **1.2.2 模型调用的最小结构：输入、约束与输出**

一次完整的大模型调用，通常至少包含以下要素：

- **角色**：模型应以什么身份工作
- **任务**：这次要完成什么
- **上下文**：完成任务需要知道什么
- **输出约束**：结果应该以什么形式返回
- **后处理**：结果如何被解析、校验和继续使用

换一种更直观的说法：先定义“它是谁”，再说明“它要做什么”，接着补齐“它需要知道什么”，最后明确“它应该怎样输出”。

在工程语境下，输入不是“最后一句用户提问”，而是一整个被组织过的上下文集合。它可能包括：

- system 提示词
- user 当前任务
- 历史消息
- 业务背景
- 代码片段
- 接口文档
- 模型参数
- 工具定义
- 输出格式要求

同样，输出也不只是“模型回答了什么”。它至少包含三层含义：

1. **内容层**：文本是否围绕任务，逻辑是否清楚
2. **结构层**：是否按要求返回，如 JSON、字段列表、代码等
3. **消费层**：结果能否被程序解析、传递或触发下一步流程

在智能体开发中，输出的价值不在于表达是否流畅，而在于下游程序能否稳定解析、校验并继续处理。

### **1.2.3 system / user / assistant 分别承担什么**

现代大模型接口通常会把消息划分为不同角色，最常见的是 system、user 和 assistant。

![Gemini_Generated_Image_s3vwuts3vwuts3vw.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/c4443b20379c47d1970f13ef3b0a2da3~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2816&h=1536&s=6246991&e=png&b=092037)

可以简单理解为：

- **system**：系统级指令，用来定义长期稳定的角色、规则、边界和输出习惯。这里的 system 不是操作系统，而是模型调用中的最高层指令。
- **user**：用户级输入，用来描述当前任务、业务材料和本次要解决的问题。
- **assistant**：模型历史回复，用来维持多轮对话中的上下文连续性。

其中，system prompt 往往最容易被忽视，却直接影响系统稳定性。可以把它理解为这项模型能力的“基础配置”。

很多初学者习惯把所有内容都写进 user：角色设定、任务要求、格式约束、背景补充全部揉在一起。短期看似能工作，但任务一复杂，就会暴露问题：Prompt 越写越长，职责边界越来越模糊，模型行为也随之不稳定。

system prompt 的价值，在于提供一层相对稳定的全局控制：

- **定义身份**：模型以什么角色理解任务
- **设定边界**：哪些事能做，哪些事不能做，信息不足时是否允许猜测
- **统一风格**：是否保持简洁、结构化、谨慎
- **减少漂移**：当 user 任务变化时，system 仍保持稳定约束

**user 解决的是“这一次要做什么”，system 解决的是“以后每一次都应该怎么做”。**

### **1.2.4 一次完整调用的基本结构**

![Gemini_Generated_Image_w2nizuw2nizuw2ni.png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/c2046051801940699367d9df3dfd42c9~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2752&h=1536&s=4372846&e=png&b=fefefe)

从工程角度看，一次适合接入系统的模型调用，可以拆成五层：

| 层级         | 作用                                       |
| ------------ | ------------------------------------------ |
| system       | 定义全局角色、规则、行为边界和输出风格     |
| task         | 描述本次调用要完成的目标                   |
| context      | 补充业务背景、代码片段、文档内容等必要信息 |
| format       | 约束输出结构，如 JSON、字段、代码格式      |
| post-process | 对结果进行解析、校验、兜底、重试、记录     |



这五层缺一不可：

- 少了 system，模型行为容易漂移
- 少了 task，目标会模糊
- 少了 context，结果容易失真
- 少了 format，输出难以消费
- 少了 post-process，系统缺少闭环

工程化的大模型调用，从来不是“把一句 Prompt 扔进去看看会发生什么”，而是在构造一套分层清晰、边界明确、可维护的调用结构。

### **1.2.5 从一次请求到一项系统能力**

适合工程系统的模型调用，不一定是最复杂的调用，而是最稳定、最可维护、最可扩展的调用。

它通常具备几个特征：

1. **分层清晰** -> 角色、任务、上下文、输出约束不应混在一段 Prompt 里。
2. **结构化输出** -> 当模型结果要进入工具调用、任务编排、状态更新时，自然语言远远不够。
3. **上下文有选择** -> 上下文不是越多越好，而是要给足关键内容，减少噪声。
4. **结果可校验** -> 模型不是数据库，也不是确定性函数。进入系统的结果必须经过解析、校验、兜底和必要重试。
5. **能力可封装** -> 不应让每个业务模块各自拼 Prompt、各自解析结果、各自处理异常。模型调用应逐步沉淀成统一能力层。

所以，真正重要的不是“会不会调模型”，而是能不能把一次调用设计得足够清楚、稳定、可复用。

## 1.3 Prompt：不是提问，而是控制

上一节我们把模型调用拆成了 system、task、context、format 和 post-process。接下来要回答的是：这些层级靠什么来控制模型？

答案是 Prompt。

Prompt 可以理解为模型调用时的指令集合。更准确地说，它不是“更高级的提问方式”，而是一份轻量级行为契约：规定模型是谁、要做什么、需要知道什么、应该如何返回，以及在什么情况下必须停止猜测。

在传统软件开发中，我们用函数签名、参数约束、返回结构和异常处理来规定一项能力如何被调用；在大模型系统中，Prompt 承担了类似职责。

**Prompt 的本质不是聊天技巧，而是一种轻量级的软件接口设计。**

### **1.3.1 角色设定：先定义模型“是谁”**

模型本质上是通用生成器。如果不限定角色，它会自行推断回答方式：有时像老师，有时像顾问，有时像程序员，有时又像聊天助手。

比如这个需求：

> 帮我分析这个需求：用户上传 Excel 后，系统自动解析数据并生成日报。

如果不设定角色，模型可能只给出泛泛描述：

> 这个需求主要是实现文件上传、数据解析和日报生成，建议考虑文件格式校验和错误处理。

这段话不算错，但太宽泛。

如果加上角色设定：

```
你是一名资深产品技术分析助手，请从系统设计角度拆解需求，输出核心模块、潜在风险和待确认问题。
```

输出就会明显收束：

- 核心模块：文件上传、Excel 解析、数据校验、日报生成、失败通知
- 潜在风险：文件格式不统一、字段缺失、数据量过大导致解析超时
- 待确认问题：日报模板是否固定、是否支持多种 Excel 格式、异常数据如何处理

角色设定的价值不是让模型“演得像”，而是让分析视角更稳定。

### **1.3.2 任务定义：明确这次要完成什么**

角色解决“它是谁”，任务定义解决“这次要做什么”。

模糊任务会带来开放输出。例如：

```
帮我看下这个功能怎么做。
```

模型并不知道你要产品拆解、技术方案、数据库设计，还是测试策略。

更好的写法是：

```
请将下面这个需求拆解为 3 个后端模块，并说明每个模块的职责：
“用户上传 Excel 后，系统自动解析数据并生成日报。”
```

代码生成也是一样：

```markdown
请使用 Python 编写一个函数，输入为用户列表，返回年龄大于 18 岁用户的邮箱地址。
要求：
1. 忽略没有邮箱的用户
2. 忽略年龄为空的数据
3. 返回结果为字符串列表
```

任务越明确，模型越容易稳定地给出你真正需要的结果。

### **1.3.3 上下文补充：提供模型原本不知道的信息**

模型再强，也不可能天然知道你的项目背景。

例如：

```
请为日报生成模块设计一个 API。
```

如果没有上下文，模型只能基于通用经验生成接口。但真实项目往往依赖更多信息：

- 系统是 REST 还是 GraphQL
- 使用什么鉴权方式
- 日报生成是同步还是异步
- 字段命名规范是什么
- 返回结构如何设计

补充上下文后，结果会更贴近系统：

```markdown
背景信息：
1. 当前项目采用 RESTful 风格
2. 所有接口都需要 JWT 鉴权
3. 日报生成是异步任务
4. 任务提交后返回 task_id
5. 接口字段使用 snake_case 命名
```

上下文的价值不在于多，而在于关键。好的上下文不是堆材料，而是筛出真正影响判断的要点。

### **1.3.4 输出约束：让结果从“能看”变成“能接”**

在工程场景中，模型输出往往不只是给人阅读，还要进入系统。仅仅表达清楚不够，还必须让下游程序能够解析字段、校验类型，并把结果继续传给工具、工作流或数据库。

例如：

```css
请分析下面这个需求，并按 JSON 返回：
{
  "summary": "",
  "modules": [],
  "risks": [],
  "questions": []
}
需求：用户上传 Excel 后，系统自动解析数据并生成日报。
```

如果还要进一步控制格式，可以明确：

```javascript
请只返回 JSON，不要输出额外解释。
所有字段必须保留；没有内容时返回空数组，不要省略字段。
```

输出约束本质上是在定义模型的返回值结构。没有输出约束的 Prompt 更接近自由对话；有了输出约束，才接近可被程序调用的接口。

### **1.3.5 边界限制：明确不要做什么**

很多 Prompt 只写“要模型做什么”，却很少写“不要做什么”。但在智能体开发里，这一点非常关键。

大模型默认倾向于给出完整、流畅、看似合理的回答。如果没有边界限制，它可能在信息不足时继续猜测，在任务模糊时自由扩展。

比如日志诊断任务中，可以明确：

```
如果日志信息不足以确定原因，请返回“信息不足，无法判断”，不要猜测具体故障点。
```

常见边界包括：

- 不要编造不存在的字段
- 不要补充未提供的业务规则
- 不要输出额外解释
- 信息不足时必须说明不确定
- 只在给定上下文内回答

边界限制的作用不是让模型减少输出，而是让系统在信息不足时能够安全失败，避免把猜测结果当作事实继续传递。

### **1.3.6 一个简单示例：从聊天式 Prompt 到工程式 Prompt**

聊天式写法：

```
帮我分析一下这个上传 Excel 生成日报的需求。
```

工程式写法：

```markdown
你是一名产品技术分析助手。

请分析以下需求，并输出结构化结果：
需求：用户上传 Excel 后，系统自动解析数据并生成日报。

要求：
1. 从系统设计角度拆解需求
2. 输出字段必须包含：
   - summary
   - modules
   - risks
   - questions
3. 每个 modules 元素需包含 name 和 responsibility
4. 如果信息不足，请在 questions 中提出，而不要自行补充业务规则
5. 最终按 JSON 返回，不要输出额外解释
```

**第二种写法不只是表达更清楚，而是在定义一次可被程序承接的接口调用**。

## 1.4 漂移：模型为什么会不稳定

如果 Prompt 是控制杆，那么这一节讨论的是：控制不到位时，系统会如何失控。

常见现象包括：同样的问题，结果不一样；前几次按要求输出 JSON，下一次突然夹带解释；有时很谨慎，有时又过度发挥；有些内容看起来合理，但仔细检查是错的。

这些不稳定并非玄学，通常来自几个明确原因。

### **1.4.1 不稳定通常表现在哪些地方**

![Gemini_Generated_Image_9ccftl9ccftl9ccf.png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/29f216819b1f4b2e8ae6b31d893438cd~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2048&h=2048&s=3869672&e=png&b=fefafa)

常见问题大致有五类：

- **结果不一致**：同样输入下，粒度、重点和表达方式变化很大
- **格式漂移**：要求输出 JSON，却夹带解释、漏字段或改字段名
- **内容跑题**：要求分析风险，却开始讲背景或方案
- **看似合理实则有误**：用自信语气补出不存在的规则、字段或结论
- **保守与过度发挥摇摆**：有时频繁说信息不足，有时又擅自补全

这些问题在聊天场景里可能只是体验问题，但在智能体系统里会直接影响流程执行。

### **1.4.2 温度参数会影响波动**

temperature（采样温度）可以理解为模型生成时的随机性控制参数：

- 温度越高，输出越发散，变化越多
- 温度越低，输出越保守，一致性越强

创意写作、文案发散可以适当提高温度；结构化分析、代码生成、参数提取等工程任务，更适合较低温度。

但温度只能减少随机性，不能替代清晰 Prompt。任务本身模糊时，低温度只会让模型“更稳定地模糊”。

### **1.4.3 上下文不足时，模型只能靠猜**

例如：

```
请为日报模块设计一个接口。
```

这个请求表面明确，实际缺少很多关键信息：系统风格、鉴权方式、同步/异步、字段命名、返回结构等。

缺口越多，模型需要猜的越多；猜测越多，输出波动越大。

很多时候，模型不是乱答，而是在填补你没有给出的空白。

### **1.4.4 任务不清楚，输出天然开放**

例如：

```
帮我分析这个功能。
```

“分析”可以指需求拆分、风险判断、技术方案、测试策略等。只要任务有多种合理解释，输出就很难稳定。

因此，减少漂移的第一步不是调参数，而是把任务说清楚。

### **1.4.5 输出约束不足，会导致格式漂移**

如果只写：

```javascript
请按 JSON 返回。
```

模型可能仍然：

- 在 JSON 前后加解释
- 漏掉字段
- 改字段名
- 把数组变成字符串
- 在无内容时省略字段

更稳定的写法是：

```markdown
请按 JSON 返回，且必须满足以下要求：
1. 顶层字段必须包含 summary、modules、risks、questions
2. modules 必须是数组
3. modules 中每个元素必须包含 name 和 responsibility
4. risks 与 questions 必须为字符串数组
5. 如果没有内容，请返回空数组，不要省略字段
6. 不要输出 JSON 之外的任何文本
```

输出稳定性的本质之一，就是约束强度。

### **1.4.6 如何收敛不确定性**

模型不稳定通常来自：

- 温度过高带来的随机性
- 上下文不足导致的猜测
- 任务定义不清造成的多义性
- 输出约束不足导致的格式漂移
- 缺乏校验机制导致错误扩散

对应的优化方式也很直接：

- 用合适温度降低随机波动
- 用关键上下文减少猜测
- 用清晰任务定义减少目标偏移
- 用输出约束降低格式漂移
- 用校验和兜底机制控制错误传播

**真正的工程能力，不是要求模型永远不犯错，而是把不确定性收束到系统可以接受的范围内。**

## 1.5 结构：让输出真正进入系统

前面我们讨论了调用结构、Prompt 控制和输出漂移。但还有一个更硬的工程门槛：即使内容大体正确，只要输出形态不可解析、不稳定，系统依然接不住。

在聊天场景里，自然语言通常足够。只要回答通顺、逻辑清楚，人就能继续理解。

但在智能体系统里，模型输出往往要进入：

- 下一个任务节点
- 工具调用参数
- 工作流状态
- 数据存储结构
- 代码执行流程
- 评测与日志系统

也就是说，模型结果必须从“能读懂”进一步变成“能处理”。关键就是结构化输出。

![image.png](https://p9-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/71385e57c5d54d6a9bb651d53a38b532~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=1376&h=768&s=298526&e=png&b=fefefe)

### **1.5.1 为什么自然语言不适合直接接系统**

自然语言最大的优点是灵活，最大的缺点也是灵活。

例如，模型自由输出：

> 这个需求大致可以分成三个部分，首先是文件上传，其次是数据解析，最后是日报生成。风险主要在于文件格式兼容性和异常数据处理上，另外还有一些待确认问题，比如日报模板是不是固定。

人能看懂，但程序很难稳定处理：

- 哪一段是模块？
- 哪一段是风险？
- 待确认问题有几个？
- 风险是字符串还是数组？
- 下一步要切分给其他 Agent 时，从哪里切？

**系统需要的不是“差不多能懂”，而是“边界明确，能稳定读取”**。

### **1.5.2 结构化输出的本质：可消费**

结构化输出不是为了“更整齐”，而是为了“可消费”。

例如按 JSON 返回：

```json
{
  "summary": "用户上传 Excel 后，系统自动解析数据并生成日报",
  "modules": [
    {"name": "upload", "responsibility": "处理 Excel 上传与基础校验"},
    {"name": "parser", "responsibility": "解析 Excel 内容并提取有效数据"},
    {"name": "report", "responsibility": "根据解析结果生成日报"}
  ],
  "risks": [
    "文件格式不统一",
    "字段缺失导致解析失败",
    "大文件可能导致处理超时"
  ],
  "questions": [
    "日报模板是否固定",
    "是否支持多种 Excel 格式"
  ]
}
```

这时，模型输出就不再只是一段文本，而是一个可传递的结果对象：

- summary 可展示
- modules 可进入架构拆分
- risks 可交给风险评估
- questions 可形成澄清清单

### **1.5.3 为什么 JSON 最常见**

JSON 不是唯一选择，但常常是默认方案，因为它：

- 层次关系清楚
- 对人类可读
- 对程序易解析
- 前后端、脚本、工作流、日志系统都容易处理

JSON（JavaScript Object Notation）是一种常见的数据交换格式，适合表达对象、数组、字符串、数字等结构化数据。但要注意：要求“按 JSON 返回”不等于结果一定稳定。字段约束、异常处理和结果校验才是关键。

### **1.5.4 结构化输出不只有 JSON**

真正重要的不是格式本身，而是输出形式是否匹配下游消费场景。

常见选择包括：

- **JSON**：通用接口结果、工具参数、状态对象
- **XML**：适合需要标签层级或历史系统兼容的场景
- **YAML**：适合配置、部署脚本、流水线定义
- **CSV**：适合二维表、批量字段导出、简单报表
- **choice / route**：适合任务分类、流程路由、Agent handoff
- **固定格式代码 / SQL / DSL**：适合直接进入执行或编译流程

结构化输出的核心不是统一格式，而是让模型结果以最适合下游接收的形式返回。

### **1.5.5 字段约束决定结构是否稳定**

只写“请按 JSON 返回”远远不够。没有字段约束，模型可能：

- 一次叫 modules，下一次叫 components
- 一次 risks 是数组，下一次是字符串
- 一次有 questions，下一次漏掉
- 一次模块字段是 name/responsibility，下一次变成 desc

更工程化的写法应明确：

```markdown
请按 JSON 返回，且必须满足以下要求：
1. 顶层字段必须包含 summary、modules、risks、questions
2. modules 必须是数组
3. modules 中每个元素必须包含 name 和 responsibility 两个字段
4. risks 与 questions 必须为字符串数组
5. 如果没有内容，请返回空数组，不要省略字段
```

到这一步，结构化输出才从“看起来有格式”，变成系统真正可以解析和处理的结果。

### **1.5.6 异常处理：让系统能安全失败**

结构化输出还必须考虑失败情况：

- JSON 解析失败怎么办？
- 字段缺失怎么办？
- 字段类型错误怎么办？
- 值超出约束怎么办？
- 信息不足时系统如何承接结果？

更稳妥的做法，是提前定义失败时的结构。例如：

```json
{
  "summary": "",
  "modules": [],
  "risks": [],
  "questions": ["信息不足，无法完成完整分析"]
}
```

异常处理的本质不是让模型永远正确，而是让系统能够识别错误、接住错误，并决定是否重试或人工介入。

### **1.5.7 小结：从自然语言生成到系统可用**

结构化输出的意义，不是让模型看起来更规整，而是让模型结果具备进入系统的条件。

自然语言适合人类交流；系统需要的是边界清晰、字段稳定、可解析、可校验的结果。

只有当输出能被系统稳定处理，后面的 Tool Calling、工作流编排、ReAct、状态管理才有继续搭建的基础。

## 1.6 封装：从一次调用到一个可复用模块

到这里，我们已经把一次调用的“输入—约束—输出”收束到可解析、可校验的结构化结果上。接下来要做的，是把一次能跑通的调用，整理成项目里可维护、可复用、可扩展的能力模块。

进入工程实践后，真正重要的问题变成：

- Prompt 以后好不好改
- 结果异常时系统怎么处理
- 不同业务是否在重复编写相同调用逻辑
- 后续加入链式调用、工具调用或会话状态时，当前代码结构是否还能承载

**模型调用进入工程系统的标志，不是会调 SDK，而是能把一次调用收束成可维护、可复用、可扩展的模块。**

![image 1.png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/7557a5eb82bc4df984f851094d3fab71~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=1376&h=768&s=309497&e=png&b=fefefe)

### **1.6.1 从最小可运行版本开始**

任何工程化封装都不应该过早抽象。先把最小链路跑通，再决定哪些部分值得抽出来：

```tsx
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

async function main() {
  const response = await client.responses.create({
    model: "gpt-5.2",
    input: "请分析这个需求：用户上传 Excel 后，系统自动解析数据并生成日报。",
  });

  console.log(response.output_text);
}

main().catch(console.error);
```

这段代码完成了三件事：

1. 创建客户端
2. 调用模型
3. 获取结果

但它只适合验证想法，不适合长期维护。因为业务逻辑、Prompt、模型参数和输出处理都混在一起。

### **1.6.2 不要把 Prompt 写死在业务代码里**

很多项目第一版会这样写：

```tsx
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

export async function analyzeRequirement(requirement: string): Promise<string> {
  const prompt = `
  你是一名需求分析助手。
  请分析以下需求，并给出模块与风险：
  ${requirement}
  `.trim();

  const response = await client.responses.create({
    model: "gpt-5.2",
    input: prompt,
  });

  return response.output_text;
}
```

问题在于：

- Prompt 写死在函数里
- 角色设定和任务描述揉在一起
- 业务函数直接依赖自由文本
- 后续加日志、重试、校验时只能继续堆代码

更合理的方式，是把可复用部分拆出来：

```css
src/
  llm/
    client.ts
    prompts.ts
    schemas.ts
    validators.ts
  services/
    requirementAnalyzer.ts
```

### **1.6.3 先定义结果，而不是直接消费自由文本**

真正让模型调用开始工程化的，不是先抽象客户端，而是先定义返回结构，也就是这项能力对外承诺返回什么数据。

```tsx
// src/llm/schemas.ts
export interface ModuleItem {
  name: string;
  responsibility: string;
}

export interface RequirementAnalysis {
  summary: string;
  modules: ModuleItem[];
  risks: string[];
  questions: string[];
}
```

这一步完成了一个关键转变：你不再只是让模型返回一段内容，而是在规定系统最终需要接收什么结构。

### **1.6.4 封装统一模型调用层**

接下来，把“发请求、拿结果、解析 JSON”抽成统一调用层：

```tsx
// src/llm/client.ts
import OpenAI from "openai";

export class LLMClient {
  private client: OpenAI;
  private model: string;

  constructor(model = "gpt-5.2") {
    this.client = new OpenAI({
      apiKey: process.env.OPENAI_API_KEY,
      baseURL: "https://api.amux.ai/v1"
    });
    this.model = model;
  }

  async generateText(systemPrompt: string, userPrompt: string): Promise<string> {
    const response = await this.client.responses.create({
      model: this.model,
      input: [
        {
          role: "system",
          content: [{ type: "input_text", text: systemPrompt }],
        },
        {
          role: "user",
          content: [{ type: "input_text", text: userPrompt }],
        },
      ],
    });

    return response.output_text;
  }

  async generateJSON<T>(systemPrompt: string, userPrompt: string): Promise<T> {
    const text = await this.generateText(systemPrompt, userPrompt);

    try {
      return JSON.parse(text) as T;
    } catch {
      throw new Error(`模型输出不是合法 JSON: ${text}`);
    }
  }
}
```

这层抽象统一了：

- 客户端创建
- 模型选择
- system / user 输入组织
- 文本结果获取
- JSON 解析

模型调用不再散落在各处业务函数里，而是有了统一入口。

### **1.6.5 Prompt 也要像代码一样可维护**

Prompt 不应嵌在业务逻辑里，而应作为可维护资源管理：

```tsx
// src/llm/prompts.ts
export const REQUIREMENT_ANALYSIS_SYSTEM_PROMPT = `
  你是一名需求分析助手。
  你必须严格按 JSON 返回。
  如果信息不足，不要猜测，而是在 questions 字段中提出。
  不要输出额外解释。
`.trim();

export function buildRequirementAnalysisPrompt(requirement: string): string {
  return `
    请分析以下需求，并输出结构化结果。

    需求：
    ${requirement}

    返回字段要求：
    1. summary: 需求摘要
    2. modules: 模块列表，每个元素包含 name 和 responsibility
    3. risks: 风险列表
    4. questions: 待确认问题列表
  `.trim();
}
```

这样后续调整 system 规则、补字段、收紧边界或做 Prompt 版本管理，都不会污染业务代码。

### **1.6.6 把业务能力收束成模块**

业务模块不再关心“如何调用模型”，只关心“需要获得什么能力”：

```tsx
// src/services/requirementAnalyzer.ts
import { LLMClient } from "../llm/client";

import {
  REQUIREMENT_ANALYSIS_SYSTEM_PROMPT,
  buildRequirementAnalysisPrompt,
} from "../llm/prompts";

import type { RequirementAnalysis } from "../llm/schemas";

export class RequirementAnalyzer {
  private llm: LLMClient;

  constructor(model = "gpt-5.2") {
    this.llm = new LLMClient(model);
  }

  async analyze(requirement: string): Promise<RequirementAnalysis> {
    const userPrompt = buildRequirementAnalysisPrompt(requirement);

    return this.llm.generateJSON<RequirementAnalysis>(
      REQUIREMENT_ANALYSIS_SYSTEM_PROMPT,
      userPrompt,
    );
  }
}
```

使用方式也变得干净：

```tsx
// src/index.ts
import { RequirementAnalyzer } from "./services/requirementAnalyzer";

async function main() {
  const analyzer = new RequirementAnalyzer();

  const result = await analyzer.analyze(
    "用户上传 Excel 后，系统自动解析数据并生成日报。",
  );

  console.log(result);
}

main().catch(console.error);
```

此时拿到的已经不是一段自由文本，而是有结构约定的结果对象。这项能力开始像正常软件模块一样工作。

### **1.6.7 结果校验、兜底和重试不是附加项**

真正进入项目后，差距不在于“能否完成一次调用”，而在于异常发生后系统能否保持稳定。

至少要考虑三件事：

1. **JSON 解析失败要有明确报错**
2. **结果结构要做运行时校验**
3. **允许安全失败或重试**

最简单的校验函数：

```tsx
// src/llm/validators.ts
import type { RequirementAnalysis } from "./schemas";

export function isRequirementAnalysis(data: unknown): data is RequirementAnalysis {
  if (typeof data !== "object" || data === null) return false;

  const obj = data as Record<string, unknown>;

  return (
    typeof obj.summary === "string" &&
    Array.isArray(obj.modules) &&
    Array.isArray(obj.risks) &&
    Array.isArray(obj.questions)
  );
}
```

接入业务模块：

```tsx
// src/services/requirementAnalyzer.ts
import { isRequirementAnalysis } from "../llm/validators";

async analyzeWithValidators(requirement: string): Promise<RequirementAnalysis> {
  const userPrompt = buildRequirementAnalysisPrompt(requirement);
  const data = await this.llm.generateJSON<unknown>(
    REQUIREMENT_ANALYSIS_SYSTEM_PROMPT,
    userPrompt,
  );

  if (!isRequirementAnalysis(data)) {
    throw new Error("模型输出结构不符合 RequirementAnalysis 预期");
  }

  return data;
}
```

再加一个简单重试工具：

```tsx
// src/llm/utils.ts
export async function withRetry<T>(
  fn: () => Promise<T>,
  retries = 2,
): Promise<T> {
  let lastError: unknown;

  for (let i = 0; i <= retries; i++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error;
      await new Promise((resolve) => setTimeout(resolve, 500));
    }
  }

  throw lastError;
}
```

接入后：

```tsx
async analyzeWithRetry(requirement: string): Promise<RequirementAnalysis> {
  const userPrompt = buildRequirementAnalysisPrompt(requirement);

  return withRetry(async () => {
    const result = await this.llm.generateJSON<unknown>(
      REQUIREMENT_ANALYSIS_SYSTEM_PROMPT,
      userPrompt,
    );

    if (!isRequirementAnalysis(result)) {
      throw new Error("模型输出结构不符合 RequirementAnalysis 预期");
    }

    return result;
  });
}
```

这类代码不复杂，但体现了一种关键工程思维：你不是在请求模型临时生成一个结果，而是在维护一项带有不确定性的系统能力。

### **1.6.8 为后续扩展留接口**

虽然这一节还没有进入 LangChain、Tool Calling 或多轮状态，但模块设计最好从一开始就留好接口。

现在的 LLMClient 虽然只做文本和 JSON 调用，但可以自然扩展出：

- 工具参数
- 会话状态
- metadata 日志与追踪
- 统一超时、重试、埋点
- 不同任务使用不同模型的路由策略

这一节的重点只有一件事：把“一次能跑的调用”，整理成“系统里可复用的能力模块”。

从 Demo 走向模块，通常需要做到：

- Prompt 不写死在业务代码里
- 有统一模型调用层
- Prompt 可维护、可版本化
- 输出可校验、有兜底
- 为链式调用、工具调用与状态管理预留扩展点

完成这些后，模型调用才真正从“示例代码”升级为“可复用能力”。

## 1.7 示例：从需求摘要到代码生成

这一节用三个递进示例串起前面的概念：

1. **需求摘要**：观察 Prompt 如何影响自然语言输出
2. **结构化输出**：让结果从“可读”变成“可消费”
3. **代码生成**：用更强约束提升代码可运行性与边界完整性

这条路径的核心，是用角色、任务、上下文、格式和后处理一步步收束输出空间。

### **1.7.1 从需求摘要开始**

需求描述：

> 运营同学每天会上传一份 Excel 文件，系统需要自动解析其中的数据，并生成一份日报。日报生成后支持导出，如果文件字段缺失或格式异常，需要给出明确提示。

如果直接让模型“分析一下”，结果往往粒度不稳定：有时偏产品描述，有时偏技术拆分，有时把风险、待确认问题和实现建议混在一起。

更合理的方式，是先定义角色与输出框架：

```tsx
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

async function summarizeRequirement() {
  const response = await client.responses.create({
    model: "gpt-5.2",
    input: [
      {
        role: "system",
        content: [
          {
            type: "input_text",
            text: "你是一名产品技术分析助手，擅长将业务需求拆解为功能目标、核心模块和潜在风险。请使用简洁、清晰的中文输出。",
          },
        ],
      },
      {
        role: "user",
        content: [
          {
            type: "input_text",
            text: `
请分析下面这个需求，并按以下三部分输出：
1. 功能目标
2. 核心模块
3. 风险点

需求：
运营同学每天会上传一份 Excel 文件，系统需要自动解析其中的数据，并生成一份日报。日报生成后支持导出，如果文件字段缺失或格式异常，需要给出明确提示。
            `.trim(),
          },
        ],
      },
    ],
  });

  console.log(response.output_text);
}

summarizeRequirement().catch(console.error);
```

这一版的重点不是代码多了几行，而是调用被设计过：模型被限定在明确框架里，输出更集中、更可预期。

### **1.7.2 从自然语言走向结构化结果**

如果结果要传给另一个 Agent、写入数据库或触发工作流，自然语言就不够了。系统需要固定字段、稳定结构和可解析结果。

还是同一个需求，可以改成 JSON 输出：

```tsx
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

async function analyzeRequirementAsJSON() {
  const response = await client.responses.create({
    model: "gpt-5.2",
    input: [
      {
        role: "system",
        content: [
          {
            type: "input_text",
            text: `
你是一名需求分析助手。
你必须严格按 JSON 返回。
不要输出额外解释。
如果信息不足，请不要猜测，而是在 questions 字段中提出。
            `.trim(),
          },
        ],
      },
      {
        role: "user",
        content: [
          {
            type: "input_text",
            text: `
请分析下面这个需求，并按 JSON 返回，字段必须包括：
- summary: string
- modules: string[]
- risks: string[]
- priority: "low" | "medium" | "high"
- questions: string[]

需求：
运营同学每天会上传一份 Excel 文件，系统需要自动解析其中的数据，并生成一份日报。日报生成后支持导出，如果文件字段缺失或格式异常，需要给出明确提示。
            `.trim(),
          },
        ],
      },
    ],
  });

  console.log(response.output_text);
}

analyzeRequirementAsJSON().catch(console.error);
```

典型输出：

```json
{
  "summary": "实现 Excel 文件上传、数据解析、日报生成与导出，并对异常文件提供明确提示。",
  "modules": [
    "文件上传与校验",
    "Excel 数据解析",
    "日报生成",
    "日报导出",
    "异常提示与处理"
  ],
  "risks": [
    "Excel 模板不统一导致解析失败",
    "字段缺失影响日报生成完整性",
    "大文件可能导致性能问题"
  ],
  "priority": "high",
  "questions": [
    "日报导出支持哪些格式？",
    "Excel 模板是否固定？"
  ]
}
```

为了让系统真正接住结果，还需要运行时校验：

```tsx
interface RequirementAnalysis {
  summary: string;
  modules: string[];
  risks: string[];
  priority: "low" | "medium" | "high";
  questions: string[];
}

function isRequirementAnalysis(data: unknown): data is RequirementAnalysis {
  if (typeof data !== "object" || data === null) return false;

  const obj = data as Record<string, unknown>;

  return (
    typeof obj.summary === "string" &&
    Array.isArray(obj.modules) &&
    Array.isArray(obj.risks) &&
    ["low", "medium", "high"].includes(String(obj.priority)) &&
    Array.isArray(obj.questions)
  );
}
```

从这一刻开始，模型输出不只是“看起来像对”，而要满足“结构上可被程序接受”。

### **1.7.3 一个简单 AI 辅助代码生成场景**

最后看一个代码生成任务：

> 写一个 Python 函数，接收一个用户列表，返回年龄大于 18 岁用户的邮箱地址，并处理空值情况。

如果约束不清楚，模型容易：

- 默认字段都存在
- 忽略空值处理
- 返回值类型模糊
- 夹带大量解释
- 生成能跑但边界不完整的代码

模糊写法：

```tsx
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

async function generateCode() {
  const response = await client.responses.create({
    model: "gpt-5.2",
    input: "写一个 Python 函数，接收一个用户列表，返回年龄大于 18 岁用户的邮箱地址。",
  });

  console.log(response.output_text);
}

generateCode().catch(console.error);
```

更工程化的写法：

```tsx
import OpenAI from "openai";

const client = new OpenAI({
  apiKey: process.env.OPENAI_API_KEY,
  baseURL: "https://api.amux.ai/v1"
});

async function generatePythonFunction() {
  const response = await client.responses.create({
    model: "gpt-5.2",
    input: [
      {
        role: "system",
        content: [
          {
            type: "input_text",
            text: "你是一名资深 Python 工程师，请输出简洁、可读、可直接运行的代码。",
          },
        ],
      },
      {
        role: "user",
        content: [
          {
            type: "input_text",
            text: `
请编写一个 Python 函数，要求如下：
1. 输入是一个用户列表，每个用户是一个字典，可能包含 name、age、email 字段
2. 返回年龄大于 18 岁用户的邮箱地址列表
3. 如果 age 为空、email 缺失或为 None，则跳过
4. 使用类型注解
5. 先简要解释思路，再输出代码
            `.trim(),
          },
        ],
      },
    ],
  });

  console.log(response.output_text);
}

generatePythonFunction().catch(console.error);
```

这个例子把前面的概念串了起来：角色设定、任务定义、边界约束和输出要求，最终都会直接影响生成代码的质量。

Prompt 的作用不是“让模型更听话”，而是在定义一份清晰的行为契约。

## 1.8 小结：如何让一次调用成为一项能力

如果把智能体开发看成一条从概念走向系统的工程路径，那么本章要完成的事情只有一件：把大模型从“会说话的黑盒”，推进到“可被系统使用的模块”。

工具调用、工作流编排、RAG、多智能体协作都很重要，但它们的前提不是掌握多少框架，而是先把一次模型调用设计成一个可控接口：

- 角色与任务边界清晰
- 上下文可管理
- 输出有明确契约
- 结果可解析、可校验
- 失败时能够安全兜底
- 调用逻辑可以封装复用

因此，从模型调用开始，并不是降低目标，而是在打地基。

**用 system / task / context / format 的分层收束不确定性，用结构化输出把“人能读懂”推进到“系统可处理”，再用 post-process（后处理）把模型结果纳入工程闭环。**

只有当这一层稳定下来，后续更复杂的能力叠加才不会放大混乱，而会沉淀为可维护、可复用、可扩展的系统能力。

接下来，我们才有资格把这些“受约束的调用”组织成工作流，接入工具与状态，真正进入智能体工程的下一阶段。
