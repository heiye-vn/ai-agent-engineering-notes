> 本篇聚焦 RAG 和上下文工程。Agent 想真正进入业务场景，不能只依赖模型参数里的通用知识，而要能读取企业文档、历史工单、代码说明、接口文档、产品规则和用户上下文。RAG 的价值不只是「接一个向量库」，而是让 Agent 的回答建立在可验证、可更新、可追溯的业务事实之上。

## 1. RAG 是什么？它解决了什么问题？

**问题**

什么是 RAG？为什么 Agent 系统经常需要 RAG？

**回答**

RAG 是 Retrieval-Augmented Generation，即检索增强生成。它的核心思路是：

    先从知识库检索相关资料
    → 再把资料作为上下文交给模型生成答案

RAG 主要解决 LLM 的几个问题：

*   模型不知道企业内部知识
*   模型知识可能过时
*   模型容易编造事实
*   不希望把所有业务知识都塞进 Prompt
*   需要答案可追溯到资料来源
*   需要业务知识可以动态更新，而不是重新训练模型

在 Agent 系统中，RAG 可以让 Agent 不只依赖模型参数，而是能读取业务文档、产品说明、历史工单、会议纪要、接口文档、代码仓库说明等外部知识。

**解读**

RAG 不应被简化成「向量数据库」。向量库只是实现手段之一。RAG 的核心是：

> 把模型生成建立在可检索、可更新、可追溯的外部知识上。

一个完整 RAG 系统至少包括：

    文档采集
    → 清洗
    → 切分
    → 向量化 / 索引
    → 召回
    → 融合
    → 重排
    → 上下文注入
    → 生成
    → 引用与评估

关键不在于列出 pgvector / Qdrant 这类工具名，而在于说明每一环如何影响最终答案质量。

***

## 2. 向量检索、BM25、Hybrid Search 有什么区别？

**问题**

向量检索、BM25 和 Hybrid Search 分别适合什么场景？

**回答**

**向量检索**基于语义相似度。它适合找表达不同但语义接近的内容。例如：

*   “登录失败”
*   “用户无法进入系统”
*   “认证流程异常”

这些表达字面不同，但语义接近。

**BM25** 是基于关键词的字面检索。它适合命中特定词、编号、配置项、专有名词。例如：

*   REQ-001
*   OAuth2
*   corpId
*   callback\_url
*   某个接口名或字段名

**Hybrid Search** 是混合检索，通常将向量检索和 BM25 结合，再用 RRF 或 rerank 进行融合排序。它兼顾语义召回和关键词精确命中。

**解读**

企业知识库中，Hybrid 往往比纯向量更稳，因为业务里大量信息依赖编号、术语、字段名、API 名称和配置项。

可以这样回答：

> 向量检索解决「意思像不像」，BM25 解决「词有没有命中」，Hybrid 解决生产环境里语义召回和关键词精确命中的平衡。

例如用户问「企业微信扫码登录回调校验什么」，向量检索可能召回「第三方登录流程」，BM25 可以准确命中「corpId」「OAuth2」「callback」等关键术语。两者结合，比单一路径更可靠。

## 3. RAG 中 chunk size 怎么选择？

**问题**

RAG 文档切分时，chunk size 应该怎么选？

**回答**

chunk size 没有固定答案，要根据文档类型、检索目标和模型上下文窗口综合选择。

一般原则：

*   chunk 太小：上下文不完整，模型难以理解
*   chunk 太大：召回不精准，容易浪费 token
*   适当 overlap 可以避免关键信息被切断（常用 chunk 长度的 10%–20% 作为重叠）
*   结构化文档应优先按标题、段落、列表、代码块切分
*   FAQ、政策文档、接口文档、代码文档应使用不同切分策略

常见做法是先设一个基线，例如 300–800 tokens，再通过 Recall\@K、命中率、人工评估和线上 badcase 持续调整。

**解读**

固定回答「500 tokens」通常不够。

更稳妥的说法是：

> chunk size 是一个评估驱动的参数，不是拍脑袋决定的。

补充几个实践点：

*   产品文档适合按标题层级切
*   接口文档适合保留完整接口定义
*   表格要避免按行切碎
*   代码文档要保留函数签名、说明和示例
*   长文档可以先按章节切，再做二级切分
*   最终效果要用真实 query 集评估

## 4. Rerank 在 RAG 中有什么作用？

**问题**

为什么召回之后还需要 rerank？向量检索 topK 不够吗？

**回答**

向量检索或 BM25 的召回结果通常只是候选集合，不一定是最适合放进 Prompt 的上下文。Rerank 的作用是对候选结果进行二次排序，把最相关、最有用、最能回答当前问题的内容排到前面。

典型流程：

    宽召回 topK=30
    → rerank 精排
    → 选 topK=5 注入上下文

Rerank 可以使用：

*   embedding 相似度重排
*   cross-encoder 重排
*   LLM rerank
*   规则加权，例如标题、更新时间、权限、来源可信度

**解读**

RAG 的目标不是召回越多越好，而是把最有用的上下文放进有限 token 窗口。

没有 rerank 时，系统容易出现：

*   召回内容相关但不够精准
*   旧文档排在新文档前
*   概念相似但业务不匹配
*   topK 里混入噪声，干扰模型回答

可以概括为：

> Recall 解决有没有找到，rerank 解决先看哪一个。

## 5. 如何判断 RAG 是否真的被 Agent 使用了？

**问题**

系统接入了 RAG，如何证明生成结果真的消费了检索内容？

**回答**

不能只看「检索函数被调用了」，还要验证检索内容是否进入模型上下文并影响最终输出。

可以从三层验证：

1.  **数据流验证**
    *   检索结果是否写入 State
    *   后续节点是否读取 State
    *   Prompt 中是否注入检索内容
2.  **行为验证**
    *   在检索内容中放入特有事实或术语
    *   检查最终报告是否正确引用这些事实
    *   资料为空时是否不编造
3.  **评估验证**
    *   构造 RAG golden cases
    *   评估 groundedness、faithfulness、引用准确性
    *   对比有 RAG 和无 RAG 的输出质量

**解读**

很多系统「看起来接了 RAG」，但生成节点并没有真正消费检索上下文。

回答时应强调：

> 代码接上不等于能力生效，必须用行为验证证明 RAG 影响了输出。

例如在知识库中注入「企业微信登录必须校验 corpId」，然后问企业微信登录方案。如果报告中正确出现 corpId，才说明 RAG 数据流闭合。

## 6. RAG 失败或超时时应该怎么办？

**问题**

如果 RAG 检索失败、向量库不可用或 embedding 模型卡住，主链路应该如何处理？

**回答**

生产系统中 RAG 不应该拖垮主链路。常见策略包括：

*   设置检索超时
*   失败时降级为空上下文
*   向量检索失败时降级 BM25
*   Hybrid 检索失败时降级纯向量或关键词
*   给用户提示「未找到相关资料」
*   记录日志和指标，便于后续排查
*   对关键场景触发告警

如果任务强依赖知识库，可以中断并提示用户；如果 RAG 只是增强上下文，可以继续执行，但明确说明资料不足。

**解读**

这里重点是区分两种失败：

*   **抛错失败**：try/catch 可以处理
*   **挂起失败**：必须用 timeout 处理

很多工程事故不是函数报错，而是远程服务或模型下载一直不返回，导致 SSE 没有任何事件，用户以为系统卡死。

所以 Agent 主链路必须有硬超时、降级和观测指标。一个成熟系统应该能回答：

*   检索失败率是多少
*   平均检索耗时是多少
*   超时后是否影响主链路
*   降级后输出质量如何
*   是否有告警和 badcase 回流

## 7. RAG 作为 Tool 和前置上下文有什么区别？

**问题**

RAG 应该作为 Agent 的一个 Tool，还是在 Agent 执行前先检索再注入上下文？

**回答**

两种方式都可以，区别在于控制权不同。

**前置检索注入**：

    用户输入 → 系统检索 → 上下文注入 → Agent 生成

优点：

*   流程可控
*   成本更容易估算
*   延迟更稳定
*   适合标准问答、需求分析、知识库增强

缺点：

*   Agent 不能自主决定是否再次检索
*   对复杂任务可能检索不充分

**RAG 作为 Tool**：

    Agent 判断是否需要知识 → 调用检索工具 → 观察结果 → 再回答

优点：

*   更灵活
*   Agent 可以自己改写 query
*   可以多轮检索
*   适合开放式探索任务

缺点：

*   成本更难控制
*   工具调用次数可能增加
*   需要更强的权限、超时和循环控制

**解读**

可以这样总结：

> 稳定业务链路优先前置检索；开放式探索任务可以把 RAG 包装成 Tool。

生产系统也可以混合使用：外层先做一次基础检索，Agent 内部在必要时再调用检索工具补充信息。

## 8. RAG 如何做评估？

**问题**

RAG 系统应该如何评估？只看答案好不好够吗？

**回答**

不够。RAG 评估至少分两层：

**检索层评估**

*   Recall\@K
*   Precision\@K
*   MRR
*   命中文档是否正确
*   rerank 后相关性是否提升
*   是否召回最新文档
*   是否召回有权限访问的文档

**生成层评估**

*   答案是否基于检索资料
*   是否编造资料中没有的事实
*   引用是否准确
*   是否回答了问题
*   是否能说明资料不足
*   输出格式是否符合要求

**解读**

RAG 的 badcase 通常分两类：

1.  没检索到正确资料；
2.  检索到了，但模型没用对。

所以评估也必须拆开看。只看最终答案，无法判断问题出在召回、重排、上下文拼接还是生成阶段。

可以补充：

> RAG 评估要把 retrieval quality 和 generation quality 分开，否则优化没有方向。

## 9. Query 侧应该如何优化？

**问题**

检索效果差时，除了调 chunk 和 rerank，query 本身可以怎么优化？

**回答**

检索质量很大程度取决于 query 和文档是否在同一个「表达空间」。常见 query 侧优化包括：

*   **Query rewriting**：把口语化、多轮指代的问题改写成完整、检索友好的查询。
*   **HyDE**：先让模型生成一个假设答案，用假设答案去检索，缓解问题和文档措辞不一致。
*   **Multi-query**：把一个问题扩展成多个角度的子 query，分别检索再合并去重。
*   **Query 分解**：把复杂问题拆成多个子问题分别检索，适合多跳问题。
*   **抽取过滤条件**：从 query 中抽取时间、模块、权限等，转成元数据过滤。

例如用户问「上个季度华东区退款为什么上涨」，可以先改写补全时间和地区，再分解为「退款金额趋势」和「退款原因分布」两个子 query 分别检索。

**解读**

Recall 上不去，往往不是向量库的问题，而是 query 和文档不在一个语义空间。

> 很多检索失败，其实是问错了，而不是没检索到。

所以 query 处理是检索质量的前置环节。工程方案里纳入 rewriting / HyDE / 分解，比单纯调整 topK 更完整。

## 10. 除了朴素 RAG，还有哪些进阶检索范式？

**问题**

朴素 RAG 在长文档、跨文档、多跳问题上会失效，有哪些进阶范式？

**回答**

*   **Parent-document / small-to-big**：用小 chunk 做检索保证精准，返回时带上其父段落或父文档保证上下文完整。
*   **Contextual retrieval**：索引前给每个 chunk 补一段所属文档的上下文说明，再向量化，显著提升召回。
*   **GraphRAG**：把知识抽成实体-关系图，适合需要跨文档聚合、多跳推理的问题。
*   **Agentic RAG / self-RAG / corrective RAG**：让 Agent 自己判断是否需要检索、检索是否充分、要不要改写后重检。

embedding 选型也要考虑：向量维度、语言覆盖、领域适配，以及是否需要针对业务语料微调。

**解读**

朴素「切分-向量-topK」在简单问答里够用，但一旦涉及长文档、跨文档聚合或多跳推理就会明显退化。

这类问题的关键，是说明 RAG 不止一种做法，并能按场景选型。

## 11. 检索到内容后，如何做上下文工程？

**问题**

检索只是「找到」，把资料放进 Prompt 还有哪些讲究？「上下文工程」具体做什么？

**回答**

上下文工程决定检索到的内容能不能被模型用好，核心手段包括：

*   **上下文预算**：给指令、历史、检索内容分配 token 预算，避免互相挤占。
*   **应对 lost-in-the-middle**：模型对上下文中间位置的信息不敏感，应把最相关内容放在首尾。
*   **去重与压缩**：合并重复片段，用摘要压缩过长上下文。
*   **结构与标注**：给每段加来源、标题、编号，方便模型正确引用和溯源。
*   **上下文隔离**：明确区分可信的系统指令与不可信的检索资料 / 网页内容，防止 Prompt Injection。

**解读**

很多系统检索没问题，但答案还是差，问题出在上下文组织。

> Recall 决定「能不能找到」，rerank 决定「先看哪个」，上下文工程决定「模型能不能用好」。

这也是本篇标题里「上下文工程」的真正含义：它不是 RAG 的附属，而是决定检索价值能否落地的关键一环。

## 本篇小结

RAG 面试的关键不是「会不会向量化」，而是能否讲清楚从文档到答案的完整链路：

    文档处理
    → 切分
    → 索引
    → 召回
    → 融合
    → 重排
    → 注入
    → 生成
    → 引用
    → 评估
    → 降级

完整回答要覆盖三件事：

1.  检索质量如何提高；
2.  检索内容如何真正影响 Agent 输出；
3.  检索失败时如何不拖垮主链路。

一句话总结：

> RAG 的目标不是把资料塞进 Prompt，而是让 Agent 的输出建立在可验证、可更新、可追溯的业务事实之上。
