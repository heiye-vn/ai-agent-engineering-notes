# 03｜Agent 工具治理生存挑战：MCP 与真实系统的 12 个事故现场

> 这一篇讨论工具调用与 MCP。Agent 接上工具后，不再只是生成文本，还能访问数据、修改系统、调用付费 API，甚至触发真实业务动作。因此，面试不能只谈 Function Calling，还要讲清楚工具治理。

🎮 **阅读方式：把自己当成正在值班的 Agent 工程师**

这不是一组看完就忘的标准答案。你将依次进入 12 个真实工程现场：先在 30 秒内做出判断，再阅读系统反馈和答案，最后接受面试官追问。

每一关都问自己三件事：**最坏副作用是什么？应该在哪一层拦截？方案失效后如何兜底？**

## 故事背景：你接手了一个电商客服 Agent

它最初只能查询订单，随后将逐步获得搜索、文件、消息、退款、数据库和内部 MCP 工具。随着能力增加，你会遇到工具误选、超时重试、权限越界、提示注入和重复扣款等事故。

你的目标是搭出一条**权限清晰、失败可控、过程可观测、关键动作可审批**的生产链路，而不是一味扩大 Agent 的行动范围。

### 通关规则

*   看到「轮到你决策」时，先暂停阅读并口述答案。
*   不只给方案，还要说出方案的边界和失败模式。
*   每关结束后按文末评分表自评。
*   能回答基础题算会用；能处理坏条件、真实副作用和方案权衡，才算生产级。

## 第 1 关：只会聊天的 Agent，能解决真实问题吗？

### 🎬 事故现场

用户问客服 Agent：「我的退款到账了吗？」模型根据历史语料生成了一段很合理的解释，但它从未查询订单或支付系统。

### ⏸️ 轮到你决策

用 30 秒回答：为什么这里不能只靠模型？如果不给 Agent 工具，它最多能做到什么？

### 💥 系统反馈

回答再流畅，也无法证明退款的真实状态。涉及实时事实和业务动作时，语言生成不能替代系统查询与执行。

### 🎤 面试官问题

为什么 Agent 不能只靠模型回答，而需要工具调用？

**参考回答**

模型本身只负责理解和生成，它不能直接访问实时数据、数据库、文件系统、业务 API 或外部服务。

工具调用让 Agent 能够：

*   **获取实时信息**：天气、股价、航班、新闻等随时间变化的数据，模型训练时并不知道，只能靠工具实时去取。
*   **查询业务系统**：订单状态、用户资料、库存余量等企业内部数据，让回答建立在真实业务现状上，而不是凭空编造。
*   **执行代码**：跑一段脚本做精确计算、数据清洗或生成图表，弥补模型不擅长的确定性运算。
*   **读写文件**：解析上传的文档、导出报告、批量改写配置，把结果真正落到文件里。
*   **调用搜索**：用搜索引擎或向量检索补上模型的知识盲区，尤其是长尾和最新内容。
*   **操作数据库**：对结构化数据做增删改查，支撑下单、建档、更新状态等业务闭环。
*   **创建任务或提交 PR**：在 Jira、GitHub 等系统里直接产生工程动作，从「给建议」变成「真的动手」。
*   **调用内部服务**：对接公司自有 API 与微服务，复用已有系统能力而不必重复造轮子。

没有工具，Agent 只能「说」；有了工具，Agent 才能「做」。

**解读**

工具调用带来能力，也带来风险。因为工具可能产生真实副作用：

*   **发消息**：给用户或群组发出邮件、IM、通知，一旦发出就收不回来。
*   **改数据库**：直接写入或更新业务数据，改错会污染真实数据。
*   **删除文件**：移除文档或资源，缺少备份时几乎不可恢复。
*   **调用付费 API**：每次调用都在真实花钱，失控就是账单爆炸。
*   **泄露敏感数据**：把密钥、隐私、内部资料带出边界，属于安全事故。
*   **修改用户资产**：改动订单、余额、权限等归属用户的东西，影响直接。
*   **触发上线流程**：启动部署、发布或审批链路，波及生产环境。

因此工具调用必须有权限、审计、白名单、超时、重试和人工审批机制。

核心原则是：

> 工具调用的目的不是扩大模型的自由，而是让它在明确的权限和边界内连接真实系统。

## 第 2 关：模型真的“调用”了函数吗？

### 🎬 事故现场

同事说：「模型已经执行了退款函数。」但你查看链路后发现，模型只生成了函数名和一段 JSON，真正执行退款的是应用服务。

### ⏸️ 轮到你决策

请用一句话区分 Tool Calling 和 Function Calling，并解释真正执行代码的是谁。

### 🎤 面试官问题

Tool Calling 和 Function Calling 是一回事吗？

**参考回答**

两者相关，但解决的问题不同。

**Function Calling** 通常指模型按照给定 schema 生成函数名和参数，然后由应用层执行对应函数。它更偏模型 API 能力。

**Tool Calling** 是更宽泛的概念，表示 Agent 可以调用各种外部能力，包括函数、API、搜索、数据库、MCP 工具、代码执行器等。

两者的关系是：

    Function Calling 是 Tool Calling 的一种实现方式

在工程系统中，工具不仅需要 schema，还需要：

*   **权限控制**：限定这个工具能被谁、在什么范围内调用。
*   **超时控制**：给每次调用设上限，避免卡死拖垮主链路。
*   **错误处理**：区分可重试与不可重试，失败时有明确兜底。
*   **参数校验**：执行前先验证参数合法，挡住非法或危险输入。
*   **调用日志**：记录每次调用的入参和结果，便于排查。
*   **审计记录**：留存「谁在何时调用了什么」，满足合规与追责。
*   **结果裁剪**：只把有用字段放回上下文，避免长文本污染。
*   **成本控制**：监控调用量与花费，防止付费接口失控。

**解读**

如果只从 OpenAI API 的角度解释，会遗漏企业系统更关心的治理问题。

完整的工具生命周期包括：

    注册 → 描述 → 授权 → 参数校验 → 执行 → 结果处理 → 审计 → 评估

Function Calling 解决的是「模型如何表达要调用什么」；工具治理解决的是「系统是否允许它调用、怎么调用、调用失败怎么办、调用后如何审计」。

**延伸：在 LLM 层面到底发生了什么**

面试官常追问「模型是怎么『调用』函数的？它并没有真的执行代码」。要点：

*   应用把工具的 JSON Schema 注入请求（对多数模型会被序列化成 system/tool 段的 token）。模型并不执行函数，它只是被约束着输出一段结构化的「调用意图」：函数名 + 参数 JSON。
*   应用层解析这段输出，真正执行的是你的代码，再把结果作为一条 `tool` 角色消息回填，模型据此继续生成。
*   所以「一次 tool call」本质是「模型输出意图 → 应用执行 → 结果回填 → 模型续写」的多轮循环。每一轮都要重新把工具定义和历史结果塞进上下文，这也是 token 成本的主要来源。
*   现代做法用 **Structured Outputs / strict 模式**（用 JSON Schema 强约束解码）保证参数一定可解析，从根上消除「模型返回的 JSON 解析失败」这类脏输出，也顺带压掉一部分「畸形输出型注入」。
*   工具极多时，新模型开始支持 **tool search**：先延迟加载少数常用工具，需要时再检索补充，避免上百个 schema 一次性挤爆上下文。

## 第 3 关：一个 `query: string` 为什么埋下了事故？

### 🔍 找漏洞

团队把所有搜索能力都封装成一个参数：

```json
{"query": "string"}
```

模型不知道该搜文档、工单还是代码，也不知道时间范围和返回数量。请先找出这份 schema 至少 3 个问题。

### 🎤 面试官问题

Agent 工具的 schema 应该如何设计？为什么 schema 很重要？

**参考回答**

工具 schema 决定了模型如何理解工具、如何生成参数，也决定了应用层能否安全执行工具。

设计时要注意：

*   工具名称要清晰，避免歧义
*   工具描述要说明适用场景和不适用场景
*   参数字段要尽量具体
*   必填字段和可选字段要区分
*   枚举值优先于自由文本
*   对危险参数要限制范围
*   对用户输入要二次校验
*   返回结果要结构化，避免长文本污染上下文

例如一个搜索工具不应该只定义：

    query: string

还可以补充：

    query: string
    topK: number
    source: "docs" | "tickets" | "code"
    freshness: "recent" | "all_time"

**延伸：schema 的工程细节**

*   MCP 和主流模型的工具参数用 **JSON Schema 2020-12** 描述。善用 `enum`、`minimum/maximum`、`pattern`、`required`、`additionalProperties: false`，把非法参数在「进入执行」之前就挡掉。
*   用 `$ref` / `$defs` 复用复杂类型很自然，但要注意有些客户端在解析 MCP 工具 schema 时会丢掉 `$defs` 定义（llama-stack 就出过这个 bug），导致嵌套类型信息在传给模型前被抹掉、参数质量下降。跨端集成时要先验证 schema 是否被完整透传。
*   危险参数要用类型收窄，而不是靠描述文字劝阻。例如文件工具别用 `path: string`，而应约束到白名单目录或用 `enum` 限定可选资源；金额、数量给 `maximum`。
*   描述里要写「不适用场景」。Paragon 的工具调用评测显示：优化工具描述对调用准确率的提升，往往比换更强模型更明显，但也最费人工。
*   输出也要有 schema。结构化、可裁剪的返回值，比一坨自由文本更利于下一步决策，也更难被返回内容里的注入劫持。

**解读**

schema 越模糊，模型越容易生成错误参数。工具描述越宽泛，Agent 越容易误用工具。

但 schema 也不是越复杂越好。字段太多会增加模型选择成本，也会让调用失败率上升。

好的 schema 要同时满足四点：

> 模型容易选择，参数容易填写，系统容易校验，出错后容易恢复。

## 第 4 关：公司有 30 个系统，你要写 30 套适配吗？

### 🎬 事故现场

搜索、数据库、Git、工单和文件系统都有自己的 SDK。每接入一个 Agent 客户端，团队都要重新实现一遍适配、鉴权和错误处理。

### ⏸️ 轮到你决策

你会怎样降低客户端与工具之间的耦合？MCP 标准化的究竟是哪一层？

### 🎤 面试官问题

什么是 MCP？为什么说 MCP 是 Agent 工具调用的标准化协议？

**参考回答**

MCP 是 Model Context Protocol。它的目标是为模型和 Agent 提供一种标准方式来连接外部工具、数据源和上下文。

没有 MCP 时，每个工具都要在应用里硬编码适配：

    Agent → 自定义搜索工具
    Agent → 自定义数据库工具
    Agent → 自定义文件工具
    Agent → 自定义 Git 工具

有了 MCP 后，工具可以作为独立 server 暴露能力，Agent 客户端在运行时发现并调用工具。

MCP 解决的问题包括：

*   **工具接入方式标准化**：所有工具按统一协议暴露，不用为每个工具单独写适配。
*   **工具和 Agent 解耦**：工具作为独立 server 存在，Agent 端不必关心其内部实现。
*   **不同客户端复用同一套工具**：一个 MCP server 可同时被 IDE、桌面端、自研 Agent 共用。
*   **工具能力可以独立部署和升级**：改工具不用动 Agent，各自独立迭代。
*   **更容易做权限、审计和治理**：统一入口让白名单、鉴权、日志有地方集中落地。

**解读**

MCP 不只是「多一种工具调用方式」，而是把工具从应用内部抽离成可复用、可治理的外部能力。

可以把 MCP 看作 Agent 世界里的 USB-C、插件协议或工具操作系统。

但生产中不能只关注「连上 MCP」，还要关注工具白名单、权限边界、连接失败降级和恶意 MCP server 风险。

**延伸：MCP 的协议骨架（能讲清楚就是加分项）**

*   MCP 基于 **JSON-RPC 2.0**，是 client–server 架构：Host（AI 应用，如 Claude Desktop / IDE）内部持有一个或多个 Client，每个 Client 连一个 Server。
*   Server 暴露三类原语，别只记得 tools：
    *   **Tools**：模型可调用、会产生副作用的能力（model-controlled）。
    *   **Resources**：只读上下文 / 数据，如文件、数据库 schema（application-controlled，很多客户端要用户显式选中才用）。
    *   **Prompts**：可复用的提示 / 工作流模板（user-controlled）。
*   能力发现是运行时的：Client 通过 `tools/list`、`resources/list` 等请求动态拿到清单，而不是编译期写死。
*   两种传输：**stdio**（本地子进程，低延迟、强隔离，但难水平扩容、生命周期绑进程）和 **Streamable HTTP / SSE**（远程，可扩容可共享，但要处理鉴权、断连重连、负载均衡）。
*   面试时可以用「AI 世界的 USB-C」帮助理解，但要紧接着说明：USB-C 也能接入恶意设备，因此协议统一并不等于连接可信。

## 第 5 关：插上“USB-C”，为什么系统反而更危险？

### 🎬 事故现场

团队接入一个外部 MCP Server，并自动注册它暴露的全部工具。一周后，某个工具描述发生变化，开始诱导模型读取密钥并调用外部 URL。

### ⏸️ 轮到你决策

请列出接入第三方 MCP Server 前必须检查的 5 项内容。哪些能力应该默认拒绝？

### 🎤 面试官问题

把 MCP 工具接入 Agent 系统时，有哪些工程注意点？

**参考回答**

主要注意以下几点：

1.  **连接生命周期**
    *   MCP server 不应每次请求临时启动，最好在进程启动时连接并复用。
2.  **工具白名单**
    *   不是 MCP 暴露什么工具，Agent 就能调用什么工具。
    *   应该默认拒绝，只允许明确授权工具。
3.  **命名一致性**
    *   工具名经过 prefix 或包装后，可能和白名单不匹配。
4.  **失败降级**
    *   MCP server 不可用时，系统应降级到 mock 工具或跳过工具，而不是让主链路崩溃。
5.  **超时和重试**
    *   工具调用必须有 timeout，避免卡住 Agent。
6.  **审计日志**
    *   记录谁调用了什么工具、参数是什么、结果是什么。
7.  **权限隔离**
    *   高风险工具需要用户授权或人工审批。

**解读**

这道题真正考查的是 MCP 接入后的治理能力。只说明「会调用 MCP SDK」还不够，还要讲清楚：

> 工具连接真实系统后，必须被安全、稳定、可观测地治理。

尤其是 MCP 工具可能来自外部 server，不能默认可信。

**延伸：为什么「不能默认可信」不是危言耸听**

Equixly 对一批热门 MCP server 的安全评估里：约 **43% 存在命令注入**、**30% 允许无限制 URL 拉取（SSRF）**、**22% 会读到目标目录之外的文件**。也就是说，你接入的 server 本身很可能就是漏洞入口。

几类已被公开记录的 MCP 特有攻击，值得点名：

*   **工具投毒（Tool Poisoning）**：把恶意指令藏在工具*描述*里，用户看不见但模型看得见，从而诱导模型泄露密钥或执行额外动作。
*   **Rug Pull / 静默重定义**：Day 1 审核通过的「人畜无害」工具，Day 7 悄悄改掉自己的定义，把参数或密钥转发给攻击者。
*   **跨 server 工具影子（Tool Shadowing）**：多个 server 接到同一个 Agent 时，恶意 server 可以覆盖 / 拦截发给可信 server 的调用。

学术上已有工作（Puppet）对 MCP 做 confused deputy 攻击，工具选择劫持率高达 90% 以上。对应的防御正是本篇反复强调的：默认拒绝 + 显式白名单、工具定义变更需要重新审核（pin 版本 / 校验 hash）、来源隔离与供应链校验、出站白名单。

## 第 6 关：Agent 选错工具，第一反应是换模型吗？

### 🎬 事故现场

Agent 在 80 个相似工具中频繁误选。团队准备直接升级更昂贵的模型，但工具名称含糊、描述重叠，所有 schema 又被一次性塞进上下文。

### ⏸️ 轮到你决策

按优先级写下前三个改进动作。你会先改模型、工具集合、描述、schema，还是审批策略？

### 🎤 面试官问题

Agent 选择了错误工具或传了错误参数，应该如何处理？

**参考回答**

可以按事前、事中、事后三层处理。

**事前**

*   工具描述写清楚适用场景
*   参数 schema 严格校验
*   工具白名单和权限控制
*   通过路由缩小可用工具集合

**事中**

*   调用前做参数校验
*   高风险工具要求确认
*   工具调用设置 timeout
*   对异常结果进行格式化返回
*   对返回内容进行长度裁剪和敏感信息过滤

**事后**

*   记录调用日志
*   将 badcase 加入评估集
*   优化工具描述和选择策略
*   必要时加入工具选择 Critic

**解读**

「让模型重新调用一次」解决不了根因。工具错误通常来自以下几类问题：

*   **工具描述不清**：模型分不清该用哪个、什么时候用，自然容易选错。
*   **可选工具太多**：候选集太大，选择噪声和 token 成本都会上升。
*   **参数 schema 太宽**：字段没有约束，模型很容易填出非法或离谱的值。
*   **缺少权限和审批**：错误调用没有被拦住，直接产生了副作用。
*   **缺少调用后评估**：没有把 badcase 沉淀下来，同类错误反复发生。

Agent 经常选错工具时，先缩小候选工具集，再优化描述、收紧参数约束并加强路由；升级模型通常不是第一选择。

## 第 7 关：一个慢工具拖死了整条客服链路

### 🎬 事故现场

库存工具响应时间从 300 ms 升到 30 s。100 个 Agent worker 同时进行三次重试，最终把仍可工作的下游彻底压垮。

### ⏸️ 轮到你决策

你会在哪里设置超时？哪些错误允许重试？如何避免重试风暴？非关键工具失败后主流程是否继续？

### 🎤 面试官问题

外部工具可能慢、失败、无响应或返回异常结果，Agent 系统应该如何处理？

**参考回答**

工具调用必须作为不可靠依赖来设计。常见做法包括：

*   **每个工具设置 timeout**：超过阈值就放弃，避免单个慢工具卡住整个 Agent。
*   **对可重试错误做有限次数重试**：网络抖动等瞬时错误重试几次即可，但要设上限。
*   **对不可重试错误快速失败**：参数非法、业务拒绝这类错误重试没用，尽早返回。
*   **对非关键工具做降级**：非核心工具挂了就跳过或用兜底，不影响主流程。
*   **对关键工具失败给出明确用户提示**：核心能力不可用时如实告知，而不是假装成功。
*   **对工具结果做 schema 校验**：返回值先验证结构，避免脏数据流入后续步骤。
*   **对工具输出做长度裁剪和敏感信息过滤**：既省上下文，又防止敏感内容外泄。
*   **记录工具延迟、失败率和错误类型**：有指标才能发现哪个工具在拖后腿。
*   **对长期异常工具熔断**：持续失败就先切断，避免反复重试压垮下游。

**解读**

Agent 工具调用本质上是微服务调用、外部 API 调用和模型决策的结合。

> 工具不是模型能力的一部分，而是真实系统依赖。既然是外部依赖，就必须配置超时、重试、降级、熔断和监控。

回答到这一层，才能体现对生产依赖治理的理解。

## 第 8 关：普通用户借 Agent 看到了管理员数据

### 🎬 事故现场

客服 Agent 使用公司的万能 API Key 查询订单。普通用户通过自然语言让 Agent 读取了不属于自己的订单，工具层却认为请求来自管理员账号。

### ⏸️ 轮到你决策

谁的身份应该传到工具层？有效权限应该由哪几个集合共同决定？如果无法透传用户凭证，如何兜底？

### 🎤 面试官问题

Agent 可以调用很多工具，权限系统应该如何设计？

**参考回答**

可以采用多层权限模型：

1.  **工具注册层**
    *   工具必须显式注册，不能动态调用任意函数。
2.  **工具白名单**
    *   每个 Agent 只能访问被授权的工具。
3.  **用户权限绑定**
    *   Agent 代表用户行动时，不能超过用户自身权限。
4.  **作用域限制**
    *   限制工具能访问的数据范围，例如项目、团队、文件夹。
5.  **风险分级**
    *   读操作低风险，写操作高风险，删除、支付、发送更高风险。
6.  **审批机制**
    *   高风险动作必须经过用户确认。
7.  **审计日志**
    *   记录工具名、参数、调用者、结果、时间。

**解读**

有效权限可以写成：

> Agent 权限 = Agent 身份权限 ∩ 用户权限 ∩ 工具作用域 ∩ 当前任务授权。

不要让 Agent 通过一把万能 API Key 绕过这些边界。

## 第 9 关：Agent 要退款，谁来按下确认键？

### 🎬 决策题

用户说：「这个订单有问题，帮我处理一下。」Agent 推断用户想要退款，并准备直接调用退款工具。

你会选择：

*   A. 只要模型置信度超过 90% 就执行
*   B. 让模型自行判断是否需要确认
*   C. 生成操作预览，由用户确认金额、订单和影响后执行
*   D. 所有工具一律人工审批

### 💥 系统反馈

C 通常更合理：审批应根据风险和可逆性分级，而不是交给模型自我约束，也不必阻塞所有低风险读取。

### 🎤 面试官问题

既然 Agent 可以自动调用工具，为什么还需要人工审批节点？

**参考回答**

因为有些动作一旦执行，就会产生难以撤销的真实影响。例如：

*   **删除文件**：数据一旦删除往往无法恢复。
*   **修改数据库**：错误写入会直接污染真实业务数据。
*   **发送邮件或消息**：发出去就收不回，还可能打扰真实用户。
*   **创建订单或支付**：涉及真金白银，重复或出错代价很高。
*   **改权限**：可能造成越权或把人误挡在门外，牵连安全。
*   **提交 PR 或部署**：直接影响代码库和生产环境。
*   **调用外部付费服务**：每次都产生真实费用，且难以回滚。

这些动作不能完全依赖模型判断。推荐流程是：

    Agent 生成计划或操作预览
    → 用户检查
    → 用户批准
    → 系统执行
    → 记录审计

**解读**

Human-in-the-loop 并不是放弃自动化，而是给高风险动作加一道安全边界。

原则很简单：

> 低风险读操作可以自动执行；高风险写操作需要审批；关键生产动作必须可回滚、可补偿或可审计。

## 第 10 关：退款超时了，你敢不敢重试？

### 🎬 事故现场

退款工具调用 10 秒后超时。日志无法确认下游是否已经执行成功，而下游既不支持幂等键，也不支持先查后写。

### ⏸️ 轮到你决策

*   A. 立即重试，优先保证退款成功
*   B. 更换参数后重试
*   C. 标记为不确定状态，停止自动重试并进入对账或人工流程
*   D. 让模型根据用户情绪决定

先选一个，再说明：如果下游支持幂等键，你的方案会如何变化？

### 💥 系统反馈

超时不等于失败。无法确认结果又无法去重时，盲目重试可能造成重复退款；这时应把“不确定性”显式建模，而不是假装调用已经失败。

### 🎤 面试官问题

工具调用失败后需要重试。遇到发消息、支付、建单这类写操作，怎么避免重复执行？

**参考回答**

先区分读写操作。读操作通常可以有限重试；写操作会产生真实副作用，重试前必须解决幂等问题：

*   **幂等键（idempotency key）**：为一次业务意图生成唯一标识，由下游保存并去重。即使请求重复到达，也只执行一次。
*   **错误分类**：参数错误、权限拒绝、业务校验失败应直接终止；网络抖动可以有限重试。超时只能说明结果未知，不能直接视为失败。
*   **执行前查状态**：如果下游支持查询，重试前先确认操作是否已经生效。
*   **并发控制**：使用唯一约束、乐观锁或版本号，挡住并发请求造成的重复写入。
*   **对账与补偿**：支付等关键动作要保留最终状态，支持人工核对、撤销或补偿。

**解读**

最危险的情况不是明确失败，而是调用方超时、下游却已经成功。此时直接重试，可能造成重复发信、重复建单或重复扣款。

> 写操作的重试，本质上是一次新的业务执行。无法确认前一次结果时，不应自动再做一遍。

因此，读写操作要采用不同的重试策略；无法保证幂等时，应把任务标记为「结果未知」，转入查询、对账或人工处理。

**延伸：调用方去重表（下游不给你幂等键时的兜底）**

理想情况是下游原生支持 `Idempotency-Key`；但很多老接口不支持。这时在工具封装层加一张「调用方去重表」，用「结构化上下文」当键，在请求真正发出前就拦截重复：

```sql
CREATE TABLE write_dedup (
  key         TEXT PRIMARY KEY,   -- 由 run_id + 步骤 + 参数 hash 组成
  params_hash TEXT NOT NULL,
  status      TEXT NOT NULL,      -- 'pending' | 'done' | 'failed'
  result      JSONB,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

执行前先查这张表：命中 `done` 就直接返回缓存结果，不再打下游。这正好覆盖「Agent 跑到一半崩了，框架从 checkpoint 恢复，同一个 tool call 又发了一次」这种 agent 特有的重复场景。

**延伸：小心「重试风暴」**

Agent 的重试是分布式问题的放大版：100 个 worker 各自对一个「变慢但没挂」的下游做指数退避重试，`100 × 3 = 300` 个请求会把本就吃力的接口彻底压垮，等于自己 DDoS 了自己。所以重试一定要配 **jitter（抖动）+ 熔断**，识别到过载信号（如 429 / 503）时应停止而不是继续重试。

## 第 11 关：五个工具一起返回，Context 被撑爆了

### 🎬 事故现场

Agent 并行查询订单、物流、库存、用户资料和知识库。五个工具返回数十万字原始内容，其中一个失败，另外几个结果之间还有依赖关系。

### ⏸️ 轮到你决策

哪些调用可以并行？如何隔离单点失败？哪些结果应该进入上下文，哪些应该落盘或只保留引用？

### 🎤 面试官问题

模型一轮可能发起多个 tool call，工具返回内容又可能很大，工程上怎么处理？

**参考回答**

**并行调用**：

*   无依赖的工具可以并行执行，缩短总延迟。
*   有依赖的工具要串行或做依赖编排。
*   并行要做错误隔离，单个工具失败不拖垮整批。
*   聚合结果时保持与每个 tool\_call\_id 的对应关系。

**大结果处理**：

*   结构化裁剪，只保留必要字段，不把原始大文本直接塞回上下文。
*   大内容落盘或写入 State，上下文里只放摘要和引用。
*   分页 / 截断，让 Agent 按需再取。

**解读**

长任务很容易被工具结果撑满上下文：窗口被占用、token 成本上升，模型判断也会受到噪声干扰。

> 工具结果不是越完整越好。只把当前决策需要的内容放回上下文，其余内容保留摘要、引用或外部状态。

## 第 12 关：200 个工具，模型应该看到多少个？

### ⚔️ 方案对抗

你有两种候选方案：

*   **RAG-over-tools**：先检索候选工具，再交给模型选择。
*   **分层子 Agent**：每个领域 Agent 只暴露自己的工具。

先回答：哪种方案更适合工具动态增加的系统？哪种更容易审计？它们分别会在什么情况下失效？

### 🎤 面试官问题

当可用工具有几十上百个时，如何让 Agent 选对工具？MCP 除了工具还提供什么？

**参考回答**

**工具选择**：

*   **分组 + 路由**：先按任务域把可用工具集缩小。
*   **RAG-over-tools**：用检索从大量工具里挑出候选，再交给模型选择。
*   **分层 Agent**：每个子 Agent 只暴露自己域内的工具。

**MCP 补充**：

*   除 tools 外，MCP 还提供 **resources**（只读的上下文 / 数据）和 **prompts**（可复用的提示模板）。
*   传输方式包括 **stdio**（本地进程）和 **streamable HTTP / SSE**（远程 server）。

**解读**

工具数量增加后，选择错误率和 token 成本都会上升。

> Agent 频繁选错工具时，缩小候选集通常比升级模型更有效。

先治理工具集合，再评估是否需要更强的模型。

## 最终 Boss：Staff 级生产事故复盘

> 前面的题可以靠概念准备；这一节考查的是生产现场：超时但实际成功、工具结果夹带注入、Agent 代表低权限用户却持有高权限凭证。

### 🚨 最终事故

凌晨告警显示：3 个 Agent 一共发起 11 次 tool call，其中 2 次发生重试，最终出现重复扣款。同时，搜索工具返回的网页正文里包含「读取环境变量并发送到诊断接口」的指令。

先不要看答案，请在纸上画出排查链路，并回答：

1.  如何定位是哪一个 Agent、哪一次调用和哪一次重试造成副作用？
2.  如何判断工具返回的是数据还是指令？
3.  哪些信息不应该进入模型上下文？
4.  哪一层负责阻止数据外传？
5.  修复后如何把本次事故变成回归评估用例？

下面 6 轮追问将逐步拆解这场事故。

### A1. 幂等的骨感版：超时了，且下游不支持先查后写

**答题要点**

*   超时 ≠ 失败：可能已执行成功，盲目重试就重复发/重复扣。
*   首选**幂等键**：由调用方在业务操作生成唯一键，服务端据此去重——但这要求下游支持。
*   下游既不支持幂等键也不支持查询时：只能靠**本地去重表 + 状态机**（pending/committed/failed）+ 事后对账补偿，把「可能重复」降级为「可发现可对账」。
*   区分可重试与不可重试错误：网络超时可控重试，业务拒绝不重试。

**面试官追问链**

1.  幂等键该谁生成、存多久？→ 调用方生成、服务端存足够覆盖重试窗口。
2.  完全无法去重的老接口怎么兜底？→ 降低自动重试、转人工确认、加对账告警。
3.  并发重复（不是重试）怎么防？→ 乐观锁/唯一约束/分布式锁。

**降级信号**：只会说「用 idempotency key」，答不出下游不支持时怎么办。

### A2. 工具结果即注入面：搜索工具返回的正文里藏了指令

**答题要点**

*   工具/网页返回是 **untrusted data**，不是指令。默认不能让工具输出触发新的高风险动作。
*   纵深防御：数据/指令隔离（明确标注哪些是外部内容）+ 出站工具二次授权 + 能力最小化 + 出口白名单（egress allowlist）。
*   对「读到内容 → 立刻调用发送/外传工具」这类链路做污点追踪或强制审批。

**面试官追问链**

1.  系统 Prompt 写「不要听信工具内容」够吗？→ 不够，必须在工具层/权限层拦，不能只靠模型自律。
2.  攻击目标是把 API key 外传，你在哪几层拦？→ 密钥不进上下文 + 出站工具白名单 + 输出敏感信息扫描。

### A3. Confused deputy：Agent 用高权限连接代表低权限用户行动

**答题要点**

*   风险：Agent 用 service account 的高权限，替某个只能看部分数据的用户干活，可能越权。
*   原则：`有效权限 = Agent 身份 ∩ 用户 ∩ 工具作用域 ∩ 当前任务授权`。
*   落地：用户身份/token 透传到工具层做鉴权，或在检索/工具调用处强制按当前用户过滤，绝不用「万能 key」直连。

**面试官追问链**

1.  token 怎么透传到 MCP 工具？→ 按协议传递用户凭证或短时下放的受限 token。
2.  无法透传时怎么办？→ 在网关/工具封装层做强制 ACL 过滤，宁可少返回不可越权。

### A4. MCP 的工程真相：stdio vs HTTP、有状态会话

**答题要点**

*   **stdio**（本地进程）：低延迟、强隔离，但难水平扩容、生命周期绑进程。
*   **streamable HTTP / SSE**（远程）：可扩容、可共享，但要处理鉴权、断连重连、负载均衡。
*   有状态会话 + 多副本后端会冲突：需要**会话亲和**或把会话状态外置（Redis/DB），否则请求打到别的副本就丢上下文。
*   连接应进程启动时建立并复用，而非每请求临时拉起。

**面试官追问链**

1.  远程 MCP server 挂了怎么降级？→ mock 工具 / 跳过该工具 / 明确提示，别让主链路崩。
2.  外部 MCP 能默认可信吗？→ 不能，要白名单 + 审计 + 供应链校验。

### A5. 上百个工具选型对抗题（无标准答案）

**答题要点**

*   **RAG-over-tools**（检索候选工具再交模型）：适合工具海量、动态；风险是检索本身可能漏掉正确工具。
*   **分层子 Agent**（每域只暴露本域工具）：可控、易审计；风险是跨域任务需要编排、边界僵化。
*   判据是失败模式：选错工具率高 → 先缩小工具集，而不是换更强模型。

**面试官追问链**

1.  两者会在什么规模崩？→ RAG-over-tools 在工具描述质量差时召回崩；分层在跨域任务多时编排崩。
2.  怎么度量「选对工具」？→ 工具选择准确率 + 参数校验通过率 + badcase 回流。

### A6. 可观测性深水区：3 个 Agent、11 次 tool call、2 次重试，扣款重复了

**答题要点**

*   每次 tool call 带唯一 `tool_call_id`，重试带 retry 序号，幂等键入日志。
*   分布式 trace 贯穿多 Agent，能定位到「哪个节点、哪次调用、哪次重试」造成副作用。
*   关键写操作记录请求/响应/幂等键/最终态，支持对账和回滚。

**面试官追问链**

1.  只有聚合日志没有 trace，能定位吗？→ 很难，缺少调用链父子关系和 id 关联。
2.  事后怎么防再发生？→ 幂等 + 该 badcase 进评估集 + 写操作审批。

## 本篇小结

工具调用让 Agent 从「会说」变成「能做」，但也把风险从文本层面推向行动层面。

一个成熟的工具调用系统需要回答：

1.  Agent 能调用哪些工具？
2.  工具代表谁的权限？
3.  参数是否可信？
4.  工具失败时怎么办？
5.  调用是否可审计？
6.  高风险动作是否需要人工确认？

最后记住这条原则：

> 工具调用不是让模型获得无限行动自由，而是让 Agent 在明确的权限、边界、超时、审计和审批机制下连接真实系统。
