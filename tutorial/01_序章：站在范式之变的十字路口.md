## 新的启程

![cleaned-image_(3).png](https://p1-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/c6bfb0601deb485ea3585cf718971fbc~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2752&h=1536&s=8393647&e=png&b=5864cc)

2013 年，我进入软件开发行业。从 Java 起步，后来尝试 Python，最终在互联网浪潮的末期来到杭州，成为一名前端工程师。

我清晰记得 2015 年前后的前端变革：Node.js 兴起，React、Vue、Angular 等框架快速普及。对长期习惯 DOM 操作和 jQuery 的开发者来说，组件化与工程化是一场剧烈冲击；而像我这样经验尚浅的“后来者”，反而因为没有太多技术债务，更容易适应新范式。

> 💡 那是我第一次真正感受到：**技术变革会重塑机会，敏捷学习与持续行动，真的能改变一个人的职业路径。**

没有学历、没有大厂背景，我的每一步都走得并不轻松。但也正是因为抓住了互联网与前端技术创新的窗口期，努力才得以转化为结果。相反，那些没能及时升级技术的人，不得不面对降薪、转岗甚至转行的压力。

如今，类似的场景正在 2025 年再次上演。随着大语言模型（LLM）持续迭代，软件开发正在从“人直接写代码”，转向“人描述目标、拆解任务、验证结果，AI 参与执行”的模式。抓住变化的人会再次获得技术红利；停滞不前的人，则可能被更快地甩在身后。

## 范式之变

![cleaned-image_(4).png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/2bcdac2bb8a040fa81b451831d13721a~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2752&h=1536&s=7576262&e=png&b=77cceb)

这一轮技术变革比上一轮更彻底。它改变的不只是开发工具和框架，更是人与机器的沟通方式。

过去，软件开发高度依赖图形界面、代码实现和工程经验。如今，自然语言正在成为新的入口。许多页面、接口、测试与业务逻辑，可以通过 AI 工具快速生成。传统开发中大量依赖手工实现的细节，正在被自动化能力覆盖。

**这对前端和后端开发者都构成了直接冲击**。

前端开发曾经强调像素级还原、复杂交互和兼容处理，但这些能力正在被 AI 快速补齐。后端开发过去关注数据库设计、接口逻辑、业务流程、高并发与安全性；如今，AI 也能辅助生成 API、测试用例、异常处理，甚至给出数据库和服务架构方案。

但问题也随之出现：当过程逐渐被 AI 黑盒化，最终结果就会成为更直接的评判标准。开发者的价值不再只是“能不能写代码”，而是能否设计任务、控制质量、理解系统，并让 AI 成为可靠的协作者。

> ⚠️ AI 并没有让工程师失去价值，而是让低层次、重复性的执行价值快速下降。工程师真正要守住的，是需求是否被正确拆解、架构是否合理、AI 生成的代码是否可靠，以及系统能否长期维护。

## 进一步的思考

过去，衡量工程师能力往往看语法熟练度、框架掌握程度、架构设计能力和业务理解深度。但在 AI 时代，这个能力模型正在被重构。

### 能力层次的重构

![cleaned-image_(5).png](https://p3-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/6f4b1528d9544df685965c248ead0804~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2752&h=1536&s=7170264&e=png&b=100f3f)

传统开发者的能力金字塔大致是：

语法 → 框架 → 架构 → 业务理解

而在 AI 时代，它可能变成：

- **底层：理解 AI 的能力边界**
  - 知道哪些任务适合交给 AI，哪些必须由人介入。理解模型的强项、弱点与风险，是高效协作的前提。
- **中层：任务分解与提示设计**
  - 编程不再只是写代码，而是把复杂问题拆解为模型可理解、可执行、可验证的任务链。
- **高层：系统设计与质量把控**
  - AI 可以生成代码和方案，但开发者必须负责架构合理性、可维护性、稳定性与安全性。
- **顶层：业务洞察与创新**
  - 真正的价值来自把 AI 能力转化为解决真实问题的产品和系统。

> 🎯 未来优秀的开发者，不一定是代码写得最多的人，而是最会设计人机协作流程，并能对最终结果负责的人。

### AI 的局限性

AI 显著提升了开发效率，但并不意味着工程能力不再重要。

- **复杂场景仍需要人类判断**：在复杂业务逻辑、性能优化、安全设计和异常边界上，AI 仍然可能给出“看起来正确”的错误答案。
- **代码质量仍然重要**：可维护性、可扩展性、团队规范与长期演进能力，依然决定一个项目能走多远。
- **不是所有人都能成为工程师**：“人人都能开发”只是表象。AI 降低了入门门槛，但也提高了优秀工程师的标准。

### 新的分水岭

这一轮变革的分水岭，不再是会不会使用某个框架，而是：

1. 能否指导 AI 完成复杂任务？
2. 能否识别 AI 输出中的问题？
3. 能否设计合理的人机协作流程？
4. 能否从执行者转变为架构师、编排者和质量守门人？

如果只是熟练使用 Cursor、Claude 等 AI 编程工具，却不理解系统本质，那么本质上仍然只是新的“业务熟练工”。这与当年只会熟练使用 jQuery、却没有跟上组件化和工程化浪潮的开发者并没有区别。

真正有价值的能力，是理解系统、拆解问题、设计流程、验证结果，并在人机协作中找到最优分工点。

> 🔑 AI 时代的软件开发，正在从“人写代码，机器执行”，转向“人设计流程，AI 协同执行，人验证结果”。如果未来开发者的核心工作是设计流程、调度工具、验证结果，那么 Agent 就不是一个遥远概念，而是这种新工作方式的系统化表达。

## 从大模型到智能体：开发一款 Agent 的渐进式路径

![cleaned-image_(7).png](https://p6-juejin.byteimg.com/tos-cn-i-k3u1fbpfcp/b7d7e95b29924831be02b8f1cdab1fd3~tplv-k3u1fbpfcp-jj-mark:1890:0:0:0:q75.awebp#?w=2752&h=1536&s=6926481&e=png&b=03142d)

很多人看今天的智能体，可能会以为它是突然出现的：模型变强了，工具变多了，于是 Agent 自然就来了。

但回到真实开发过程会发现，智能体不是某一天被“发明”出来的，而是在开发者不断解决问题的过程中逐步演化出来的。

真实的软件开发从来不是一次回答就能完成，而是一连串动作：理解需求、拆解任务、查阅资料、调用系统、生成结果、运行验证、修复问题、持续迭代。智能体开发，正是围绕这条链路一步步形成的。

需要说明的是，下面这条路径并不是严格的技术发明时间线，而是一条更适合开发者理解 Agent 工程化的学习路径。

------

### 1. 先让模型可用：Prompt、结构化输出与可控性

开发智能体的第一步，不是让模型自主行动，而是先让它稳定、可控、可复用。

早期最常见的问题不是模型不够聪明，而是输出不稳定：同一个问题，每次回答都不同；有时格式不对，有时逻辑不完整，有时甚至一本正经地胡说八道。

因此，最先被重视的能力包括：

- Prompt Engineering
- 角色设定
- 输出格式约束
- 结构化响应
- 上下文注入

这个阶段的目标，是把模型从“随机发挥的黑盒”，变成“能稳定完成单点任务的模块”。

------

### 2. 再让模型接入流程：LangChain 与工作流编排

当模型能完成单点任务后，新的问题出现了：真实任务往往由多个步骤组成。

例如一个代码需求，可能要经历需求理解、上下文分析、模块拆分、代码生成、测试补齐、结果校验和问题修复。单次调用已经不够用，开发者需要把模型组织进一条可执行链路。

LangChain 这类框架的价值正在于此：它不只是封装模型调用，而是把模型、提示词、工具、记忆、检索和输出解析组织成可复用的调用链路，让开发者可以把一次调用扩展为多步流程，并在流程中插入判断、解析、路由和校验。

从这里开始，开发者不再只是“调用模型”，而是在“编排模型能力”。

------

### 3. 让模型真正能做事：Tool Calling / Function Calling

即使流程搭好了，模型仍然有一个天然限制：它会生成内容，但不会真正行动。

它可以告诉你“应该查数据库”“应该打开文件”“应该调用接口”，但如果没有工具接入，它自己无法完成这些动作。

因此，Tool Calling / Function Calling 自然出现。它的本质，是给模型接上“手和脚”。

常见工具能力包括：

- 文件读写
- 数据库查询
- Shell 命令执行
- 浏览器访问
- API 调用
- 代码编辑
- 搜索与检索

从这个阶段开始，模型不再只是回答问题，而开始具备执行任务的能力。

------

### 4. 让模型边想边做：ReAct

有了工具之后，新的问题变成：

- 什么时候调用工具？
- 调用哪个工具？
- 工具返回后下一步做什么？
- 结果不对时是否会调整策略？

如果没有机制约束，模型要么只会空想不行动，要么乱调工具。ReAct 的关键不是让模型一直思考，而是让它在推理、调用工具、观察结果之间形成闭环：

1. 判断当前要做什么；
2. 调用工具获取信息；
3. 根据结果继续分析；
4. 执行下一步动作；
5. 直到完成目标。

从这个阶段开始，智能体才真正具备“围绕目标持续工作”的雏形。

------

### 5. 让模型知道它不知道什么：RAG

当智能体开始执行任务后，知识缺口会越来越明显。模型并不知道你的项目、团队规范、私有 API、业务流程和代码约定。

这时，仅靠模型参数中的通用知识已经不够。RAG 的价值，是让模型在回答或行动前先检索外部知识，再基于资料完成任务。

对 AI Coding 来说，获取项目上下文几乎绕不开。RAG 是其中一种重要方式，尤其适合处理文档、知识库、历史需求和大规模代码语义检索。

------

### 6. 让外部能力标准化接入：MCP

当工具和知识源越来越多，另一个工程问题会出现：每接一个系统都要重新适配，调用方式也不统一。

MCP（Model Context Protocol）的价值，是为智能体连接外部世界提供标准协议。它解决的是接入层标准化问题，而不是模型推理能力本身的问题。它可以把外部能力抽象为：

- **Tools**：可调用的操作能力
- **Resources**：可读取的上下文资源
- **Prompts**：可复用的提示模板

简单说：

- Tool Calling 解决“模型能不能调用工具”；
- MCP 解决“不同工具和资源能不能以统一方式接入”。

------

### 7. 把经验沉淀下来：Skills

如果说 MCP 解决的是外部能力接入，那么 Skills 更像是在解决内部经验复用。

团队真正有价值的，往往不是单个 Prompt，而是长期积累下来的工作流、排障步骤、代码规范、诊断脚本、模板方法、领域知识和最佳实践。

Skills 可以理解为一种能力封装方式：把团队反复使用的流程、规范、脚本和模板沉淀成可复用的能力包。它不一定是统一标准，但代表了智能体工程化中非常重要的一类实践。这样，智能体不再只是临场发挥，而是能够稳定调用组织沉淀下来的经验。

------

### 8. 从单体到协作：Handoffs & Subagents

当任务越来越复杂，单个 Agent 很容易出现上下文膨胀、职责混乱和推理链过长的问题。

这时，多智能体协作就成为自然选择：不同 Agent 承担不同职责，并通过 Handoffs 完成任务交接。Subagents 强调角色拆分，Handoffs 强调任务转交，多智能体协作则强调多个专职 Agent 围绕同一目标共同工作。

例如：

- 需求 Agent 负责拆解目标；
- 检索 Agent 负责查资料；
- Coding Agent 负责生成代码；
- Review Agent 负责校验质量；
- Testing Agent 负责执行验证。

**多智能体不是为了概念更炫，而是复杂任务下更合理的职责分工**。

------

### 9. 从能跑到能上线：Tracing、Evals 与工程化

当模型、流程、工具、RAG、MCP、Skills 和多智能体都接入后，一个 Agent 原型看似已经完成。但要真正上线，还必须回答更工程化的问题：

- 每一步是怎么决策的？
- 哪一步出错了？
- 为什么会失败？
- 哪个 Prompt 或工具导致了偏差？
- 效果是否持续变好？
- 成本和时延是否可控？
- 是否存在风险操作？

这时，Tracing 和 Evals 就非常关键。

**Tracing** 用来记录智能体运行过程，包括工具调用、任务流转、关键中间结果和失败位置。

**Evals** 用来系统评估智能体效果，包括输出质量、任务成功率、工具使用正确率、稳定性、安全性、成本与时延。

也就是说，只有到了这个阶段，智能体开发才真正从“会做 Demo”进入“会做系统”。

------

把整个过程串起来，会发现：

> ✨ **开发一款智能体，并不是学习几个新概念，而是把大模型逐步组织成一套可控制、能执行、可接入外部系统、可复用经验、可追踪和可评估的工程体系。**

这些概念对应的问题如下：

| 概念            | 解决的问题     |
| --------------- | -------------- |
| Prompt          | 模型可控性     |
| LangChain       | 流程编排       |
| Tool Calling    | 执行能力       |
| ReAct           | 思考与行动闭环 |
| RAG             | 知识缺失       |
| MCP             | 接入标准化     |
| Skills          | 经验复用       |
| Handoffs        | 复杂任务分工   |
| Tracing / Evals | 工程化落地     |



这样一来，它们就不再是零散术语，而是一条清晰的智能体开发路径。

## 本书的学习计划

这本书不打算把智能体开发拆成一堆零散概念，而是希望沿着更贴近真实开发的路径，带领读者理解：一款智能体如何被设计、开发，并最终落地到真实项目中。

全书将分为三个模块。

### 1. 掌握智能体开发的基础能力

这一部分从基础模型调用入手，逐步进入 Prompt 设计、结构化输出、上下文管理与工作流编排。读者会接触 LangChain、Tool Calling、ReAct、RAG 等核心概念，并理解它们分别解决什么问题。

重点不是“会使用几个工具”，而是理解一款智能体为什么需要这些能力，以及它们如何组合成可执行的系统。

### 2. 完成一个完整的 Agent 开发过程

具备基础能力后，本书会进入工程化开发阶段：如何接入外部系统，如何通过 MCP 统一能力接入，如何利用 Skills 沉淀经验，如何管理记忆与状态，如何追踪执行过程，如何评估效果，以及如何处理安全、权限、成本和可观测性等问题。

这一阶段的目标，是带领读者从“会做 Demo”走向“会做系统”。

### 3. 工具使用与开发经验分享

除了完整的 Agent 开发流程，本书还会穿插介绍各类 AI 工具的使用方式，并结合实际开发过程，分享个人在 AI Coding 与智能体开发中的实践经验、问题思考与方法总结。

这一部分不只关注工具怎么用，更关注在真实场景中如何选择工具、组合工具，并通过持续试错形成自己的开发方法。
