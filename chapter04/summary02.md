# 第四章教程总结：LangChain 进阶——记忆、工具与多 Agent

> 来源：《AI Agents 开发实践》第四章（feat/agent-memory-tools 分支）
> 核心命题：单次调用跑通之后，系统如何从「一次性问答接口」演进为「可持续对话、可沉淀制品、可拆解协作」的业务处理单元
> 四项能力主线：Memory（多轮上下文）→ Tools（真实数据读写）→ Embeddings/Vector Store（语义基础）→ Multi-Agent（角色拆分编排）
> 本章不含实现细节，只梳理知识点与企业场景扩展

---

## 一、本章要解决的四类断点

第三章解决的是「单次调用如何做对」，本章解决的是「多次调用之间如何不断线」：

| 断点 | 表现 | 对应能力 |
|---|---|---|
| 上下文断裂 | 第二轮补充的信息（需求单号、约束），第三轮模型已"失忆" | Memory |
| 事实盲区 | 模型不知道需求单详情、规范文档内容，只能靠提示词补全事实 | Tools |
| 语义检索缺失 | 规范/标准是普通文本，无法按语义召回，为 RAG 留地基 | Embeddings + Vector Store |
| 任务过载 | 一个 prompt 干所有事，职责不清、扩展困难 | Multi-Agent |

关键认知：**多轮需求沟通的质量，取决于系统能否把分散在多轮中的信息稳定组织成同一个任务上下文**，而不是某一轮回复是否完整。

## 二、Memory：会话上下文管理

### 2.1 核心知识点

- **`messages` 是跨模型的统一消息抽象**，也是 Memory、历史裁剪、多轮链路的共同基础。
- **`RunnableWithMessageHistory` 的本质**：把「历史读取 → 注入 prompt → 结果保存」统一抽象进 Runnable 链路，接口从围绕"单次请求"工作转向围绕"会话"工作。
- **`sessionId` 隔离**：不同会话各自独立，这是多租户/多用户的基础语义。
- **会话生命周期的四个动作**：
  - 读历史（getHistory）→ 注入上下文
  - 写结论（appendMessage）→ 把最终结论作为一轮完整消息写回
  - 清会话（clearSession）→ 重置上下文
  - 裁剪（trimMessages）→ 控制成本
- **旧式 `BufferMemory` / `SummaryMemory` 已不是主线**：当前 LangChain JS 体系以消息历史实现更统一、更贴近应用层设计。
- **教程链路 vs 生产链路的分层**：`InMemoryChatMessageHistory` 只适合开发阶段；生产环境历史持久化到数据库（messages 表），由服务层转成 `BaseMessage[]` 再喂给链路——**存储可替换，接口不变**。

### 2.2 消息裁剪的企业场景扩展

`trimMessages` 的知识核心：长对话不能把全部历史原样塞回模型，要有策略地保留"最近且必要"的上下文。

企业真实场景中的上下文管理有三条主流路线，由简到繁、由粗到细：

| 维度 | ① 纯滑动窗口（trimMessages） | ② 摘要压缩 + 滑动窗口 | ③ 结构化实体记忆抽取 |
|---|---|---|---|
| 核心思路 | 只保留最近 N tokens，超出直接丢 | 旧历史由小模型压成一段摘要，「System + 摘要 + 最近几轮原文」一起进 prompt | 对话中关键变量抽成状态 JSON 存 Redis/DB，prompt 只带「系统提示 + 状态 JSON + 最近消息」 |
| 信息保真度 | 低（裁掉即消失） | 高（关键信息浓缩进摘要：单号、项目类型、核心诉求） | 最高（关键字段结构化存储，永不丢失） |
| 每轮成本 | 低且稳定 | 低 + 超阈值时一次摘要调用（用便宜小模型） | 低 + 每轮一次实体抽取调用 |
| 实现复杂度 | 最低（现成 API） | 中（摘要更新时机、频率控制） | 最高（Schema 设计、状态读写、一致性） |
| 典型场景 | 即时客服/工单、单任务问答（代码查错、文案润色） | 长周期咨询、需求澄清、ERP 类大项目跟进 | 高阶 Agent、多轮表单、协同助手（单号、决策结论必须沉淀） |
| 失败模式 | 早期核心诉求被遗忘 | 摘要质量依赖小模型，可能丢细节/引入幻觉 | 抽取遗漏或错误会污染状态且难察觉 |

关键认知：

- **三种方式不互斥，是递进组合**：企业系统常见搭配——③ 保底关键字段 → ② 维持长会话语义连贯 → ① 作为最终 token 保险丝（防摘要+原文仍超窗）。
- **② 是性价比最高的企业方案**：既省 Token 又不丢关键信息；但摘要触发要控频率，否则对话密集时摘要成本反超省下的 token。
- **③ 本质是把「记忆」从文本问题降级为状态管理问题**：与结构化抽取（extractAgent / Schema）一脉相承——字段既然是结构化的，就别让模型每轮从长文本里重新"推理"它们；`clarifyAgent` 判断「信息是否充分」的对象应该是状态 JSON，而不是原文。
- **maxTokens 经验值**：客服场景 4000~8000（约 5~10 轮宽松对话）；需求分析这类单轮内容重、含大 JSON 工具返回的场景建议 8000+ 并留工具结果余量。

企业实践要点：

- **裁剪在注入 prompt 之前执行**，而不是在存储层做——存储层保留全量（审计/回溯需要），裁剪只影响本次发给模型的内容。
- **Token 成本是运营成本**：B 端产品按席位收费时，无裁剪的长会话直接吃掉毛利；裁剪策略要与产品定价模型一起设计。
- **多实例部署下 InMemory 不可用**：会话粘性（sticky session）或 Redis/DB 持久化必须二选一，否则用户换一个 pod 就"失忆"。
- **记忆写回优先 appendMessage 而非重跑模型**：最终结论直接写回历史，避免一次多余的模型调用——既省成本又保证结论一致性。

## 三、Tools：让模型接触真实数据

### 3.1 核心知识点

- **分工原则不变**：模型负责决定「是否调用、调用哪个、何时继续」；工具负责返回确定性结果。
- **业务工具优先于通用工具**：`query_requirement(id)` 比"任意读文件"更接近真实系统的能力边界——工具定义本身就是业务建模。
- 三类工具职责：**查数据**（返回事实）、**读规范**（返回规则依据）、**写制品**（产生持久化输出）。
- **输出沉淀为制品（artifact）**：只返回聊天回复，结果无法复用；写入 reports/ 才具备复核、归档、协作价值。
- **路径沙箱是硬约束**：安全校验必须放在工具内部（代码层），不能依赖模型"自觉遵守"提示词。

### 3.2 企业场景扩展

- **写权限收敛**：生产环境不应暴露通用 `write_file`，而是收敛为明确的业务动作（生成报告、更新工单状态、写入数据库记录）——让模型决定业务动作，而不是让模型决定任意文件路径。
- **审计日志**：写入类工具每次调用必须记录 who/when/what/where，写入行为可追溯、可回滚。
- **工具即 API 治理对象**：工具需要版本化、限流、超时、幂等设计——工具在 LLM 应用中的地位等同于微服务里的 RPC 接口。
- **工具循环要有上限**：模型可能反复调工具不收敛，循环次数上限 + 超限 fallback（转人工）是生产必备。
- **典型企业工具面**：工单系统查询、CRM 客户档案、知识库检索、内部审批流触发——都是"读确定性数据 + 写确定性动作"的延伸。

## 四、Embeddings + Vector Store：语义基础设施

### 4.1 核心知识点

- **本节定位**：不是 RAG，是 RAG 的地基——把业务文本（规范、验收标准、约束）转换成"可语义召回的对象"。
- **两个方法的分工**：`embedQuery()` 服务在线检索（单条输入），`embedDocuments()` 服务离线批量灌库——上层调用方式不依赖底层实现。
- **本地嵌入模型 vs API 的权衡**（以 Xenova MiniLM 为例）：

| 维度 | 本地小模型（384 维） | API（如 text-embedding-3-small，1536 维） |
|---|---|---|
| 语义精度 | 较低 | 高 |
| 成本 | 零（不消耗 token） | 按量计费 |
| 数据出境 | 无（数据主权友好） | 有 |
| 依赖 | 无网络、无密钥 | 网络 + 密钥 |
| 适用 | 教学、离线验证、敏感数据内网 | 生产知识库、大规模检索 |

- **三个概念要分清**：模型权重（磁盘缓存，一次下载反复用）、运行时内存（推理占用，进程退出释放）、向量存储（数据层，决定重启是否丢失）。
- **接口不依赖实现**：教学用 MemoryVectorStore，生产切 pgvector，上层调用不变——抽象层的价值在切换成本上体现。
- **本地模型的工程细节认知**：mean pooling + L2 单位化后，余弦相似度退化为点积，检索更快。

### 4.2 向量存储的企业场景扩展

- **存储选型谱系**：
  - `MemoryVectorStore`：仅教学演示，重启即丢
  - **PostgreSQL + pgvector**：已有 PG 技术栈的首选，向量与业务数据同库、事务一致、运维零增量——中小规模知识库的主流方案
  - Milvus / Qdrant / Weaviate：亿级向量、高 QPS 检索的专用方案
  - Redis：会话记忆 + 短时效召回的混合场景
- **灌库内容结构化**：需求规范、验收标准、约束说明分类入库，检索时可按类型过滤（metadata filter）。
- **生产 RAG 链路的完整形态**（教程第五章预告）：文本切分（chunking）→ 嵌入 → 写入 `document_chunks` 表 → pgvector `<=>` 距离排序召回 → 召回片段注入 prompt 的 `retrievedContext`。
- **混合检索是常见演进**：纯向量召回对专有名词/编号不敏感，企业实践中常叠加关键词（BM25）+ 向量的混合检索与重排序（rerank）。
- **嵌入模型切换的隐性成本**：换模型必须全量重建向量库（维度和语义空间都变了），选型时按"三年不换"的标准评估。

## 五、Multi-Agent：角色拆分与编排

### 5.1 核心知识点

- **引入多 Agent 的判断标准**（最重要的一条知识）：

| 信号 | 结论 |
|---|---|
| 一个 prompt + 少量工具能稳定解决 | 不需要多 Agent |
| 任务天然分阶段、分角色、分工具 | 适合 |
| 不同角色需要不同工具集或不同模型配置 | 适合 |
| 需要较强扩展性、角色会持续增加 | 非常适合 |

- **五个专职角色的拆分逻辑**：extract（抽取结构化字段）→ clarify（判断信息是否充分）→ analysis + risk（并行）→ summary（汇总）——按职责边界拆，而不是按流程步骤硬拆。
- **每个 Agent 就是一条独立小链**（prompt → model → parser），与第三章链式编排同构，只是职责分给了不同的链。
- **澄清短路**：信息不足时提前返回 `clarificationQuestions` 并终止流程，不硬着头皮编造——这是"承认不知道"的工程化表达。
- **失败 fallback**：全链路异常时返回 `manual_review` 转人工，多 Agent 系统必须有降级出口。

### 5.2 五种编排模式对比（企业选型）

| 模式 | 流程特点 | 典型企业场景 | 风险/成本 |
|---|---|---|---|
| Fixed Workflow | 步骤预先固定 | 需求分析、报告生成等流程稳定的流水线 | 灵活性最低，但可控、可测、可审计 |
| Router | 先分类再路由，一个入口多出口 | 客服分流（功能需求/缺陷/咨询）、工单分类派发 | 分类错误会全链路错，路由质量是生命线 |
| Supervisor | 主 Agent 按执行结果动态决策下一步 | 复杂工单处理：发现合规问题临时拉合规 Agent，高风险拉风控 Agent | Token 成本高、行为不确定，需要严格的可观测 |
| Handoff | 控制权 + 上下文一起移交 | 售前收集 → 售后评审 → 通知发送的多阶段流转 | 上下文交接时信息损耗是主要坑 |
| Planner-Executor | 先规划子任务清单，再逐步执行 | "把 PRD 拆成可排期需求清单"等开放复杂任务 | 计划可能脱离实际，需要异常回传重新规划 |

- **企业选型原则：从 Fixed Workflow 起步**。流程确定时先跑通跑稳固定编排，动态调度、路由都是后续扩展——一上来就 Supervisor 是最常见的过度设计。
- **成本意识**：5 个 Agent 意味着一次请求至少 5 次模型调用；并行（Promise.all）只能压延迟，压不掉调用次数。多 Agent 的收益必须显式大于成本时才上。
- **可观测性是前提**：每次编排要返回 `usedAgents`、`steps`、`fallback` 等执行轨迹，否则线上出问题无法定位是哪个角色出的错。

### 5.3 澄清机制的企业价值

- 「信息不足 → 显式产出澄清问题」是多轮对话系统的通用模式：与其让模型基于残缺信息编造结论，不如把信息缺口显式抛回给用户。
- 适用于：需求收集、开单前信息补全、表单预填确认等一切"输入质量决定输出质量"的 B 端场景。

## 六、统一入口：能力收束

### 核心知识点

- 四项能力各自 demo 化后必须收敛为一个业务接口（`analyze(sessionId, input)`），否则停留在分散的技术验证。
- 统一入口的职责链：多 Agent 分析 → 需要澄清则短路返回 → 报告落盘为制品 → 最终结论写回会话记忆。
- **关键设计：写回记忆用 appendMessage（直接写结论），而不是把原始输入重新交给模型跑一遍**——省一次模型调用，且历史中的结论与报告严格一致。
- 收束后的系统特征：**历史可延续、需求可查询、规范可读取、分析可拆解、结果可落盘、结论可写回**——从问答接口变成业务处理单元。

## 七、贯穿全章的工程思想

1. **演进式架构**：每项能力都从"演示能跑"到"标注生产差距"（InMemory → DB/Redis、MemoryVectorStore → pgvector、通用工具 → 业务工具收敛），教程本身在示范"教学实现 → 生产实现"的分层思维。
2. **接口与实现分离**：模型工厂、Embeddings 抽象、存储替换，全部遵循"上层调用不变，底层随时换"——这是应对 LLM 生态快速迭代的唯一防御手段。
3. **安全默认不信任模型**：路径沙箱放代码层、写权限收敛、循环设上限、失败有 fallback——模型是概率系统，确定性约束必须由工程层兜底。
4. **每个阶段留验收点**：多轮记忆不失忆、越权路径被拒、语义检索召回相关片段、信息不足触发澄清——能力验证先于功能堆叠。
5. **Token 是一等公民成本**：裁剪策略、本地嵌入模型、appendMessage 代替重跑、多 Agent 前先评估必要性——LLM 应用的架构决策里有相当比例是成本决策。
