# 第六章教程总结：让 AI 做更懂你的交互——AI 驱动 UI

> 来源：《AI Agents 开发实践》第六章（feat/ai-ui 分支）
> 核心命题：把模型输出从「给人阅读的文本」升级为「前端可渲染、用户可操作的 UI 指令」
> 主线：UI 响应协议设计 → Structured Output 约束 → 交互状态机闭环 → 前端组件渲染层 → 流式适配
> 本章不含实现细节，只梳理知识点、选型对比与实践原则

---

## 一、纯文本回复的天花板

模型输出 Markdown/纯文本，在 demo 阶段成本最低，但进入真实产品后有四个硬伤：

1. **用户需要"阅读理解"**：关键选项混在文字里，用户得自己提取信息
2. **操作路径不明确**：用户要打字回复"我选第一个"，输入方式不确定、易出错
3. **前端无法做交互增强**：一段字符串变不成可点击的卡片
4. **后续流程难以衔接**：用户选择后，系统还要再解析一次自然语言来理解选择——把确定性的操作降级成了概率性的语义理解

**核心思路**：模型返回结构化 JSON（带 `type` 字段的 UI 组件指令），前端按 type 渲染组件，用户操作后把结构化结果回传——**把"自然语言理解"从交互回路中剔除，换成确定性协议**。

---

## 二、UI 响应协议设计

### 2.1 五条设计原则

| 原则 | 含义 |
|---|---|
| **type 字段是唯一标识** | 前端只看 type 决定渲染哪个组件，不猜测、不推断 |
| **每个组件自包含** | 一个 UIResponse 携带渲染所需的全部信息，前端无需二次请求 |
| **操作可回传** | 选择/提交/确认都能以结构化 UIAction 回传给后端 |
| **可组合** | 一次回复可含多个组件（一段文字 + 一组选择卡片） |
| **向后兼容** | 新增组件类型不影响已有类型的渲染 |

### 2.2 八种组件类型总览

| type | 用途 | 典型场景 | 用户操作 |
|---|---|---|---|
| `text` | 纯文本/Markdown | 对话回复、解释说明 | 无（仅展示） |
| `selection` | 单选/多选卡片 | 选需求类型、选分析维度 | 点击回传 selectedId |
| `form` | 动态表单 | 补充需求详情、验收标准 | 填写提交回传 formData |
| `confirmation` | 确认对话框 | 确认提交、确认执行 | 确认/取消回传 confirmed |
| `card` | 信息展示卡片 | 详情、报告、进度 | 展示 + 可带操作按钮 |
| `steps` | 步骤进度条 | 流程阶段展示 | 无 |
| `table` | 数据表格 | 列表、批量数据 | 可选行点击 |
| `action_buttons` | 操作按钮组 | 快捷入口、流程分支 | 点击回传 actionId |

**协议三层结构**：`AIUIResponse = message（必填文字） + components[]（可多个组件） + context（sessionStage 流程阶段 / collectedData 已收集数据）`。message 永远存在是兜底——即使组件渲染失败，用户至少能读到文字。

### 2.3 UIAction：操作回传的统一契约

用户操作按 payload 类型区分：`select`（选择）、`submit`（表单）、`confirm`（确认）、`click`（按钮）、`row_select`（表格行）。**一套 action 协议覆盖全部组件的操作回传**，后端不用为每种组件设计独立接口。

## 三、Structured Output 约束模型输出

### 3.1 核心机制

- 用 LangChain 的 `withStructuredOutput(ZodSchema)` 把协议注入模型调用，确保输出严格符合结构
- **`z.discriminatedUnion` 而非 `z.union`**：基于 type 字段精确匹配，校验性能更好、错误信息更清晰，与"前端只看 type"的设计对齐

### 3.2 两个关键认知（面试高频）

**① Schema 只能约束"格式"，不能约束"判断"**——它能保证输出的是合法 selection，但不能保证该用 form 时模型不返回 selection。生产环境需要两层防护：

| 防护层 | 手段 |
|---|---|
| 第一层：Prompt 场景指引 | System Prompt 中明确"什么场景用什么组件"的选择指南 |
| 第二层：服务端后处理校验 | 空选项的 selection 过滤掉、message 为空补兜底文案、组件数量超限截断、异常输出降级到确定性流程 |

**② 缺少数据约束时，LLM 会一本正经地编造数据**——教程中"查看需求详情"场景，模型自己编了编号、提交人、优先级等看似合理但完全虚构的字段。生产原则：**展示需求/订单/客户等结构化数据时，事实必须从数据库或可信服务获取，模型只负责组织表达和生成 UI 指令**。这是"AI 生成交互"与"AI 编造事实"的分界线。

## 四、完整交互闭环：确定性状态机

### 4.1 四阶段流程

```
select_type（选择需求类型 selection）
   ↓ select
fill_detail（填写详情 form）
   ↓ submit
confirm（确认提交 confirmation + card）
   ↓ confirm / 取消回退
result（结果展示 steps + card + action_buttons）
```

### 4.2 双通道架构：状态机 vs LLM 自由生成

本章最重要的架构决策，路由分两条通道：

| 通道 | 路由 | 驱动方式 | 特点 |
|---|---|---|---|
| **确定性状态机** | `POST /chat` + `POST /action` | 服务端 SessionContext（stage + collectedData）推进 | 稳定、可测、回退可控；不依赖模型 |
| **LLM 自由生成** | `POST /generate` | `withStructuredOutput` 让模型自由产出 UI 协议 | 灵活、能理解任意输入；但有不确定性 |

**降级兜底**：generate 通道的输出若未通过本地 Zod 校验，自动降级到同一套确定性状态机，仍返回合法的 AIUIResponse——**不把解析失败暴露成 500**。

### 4.3 什么交给模型、什么交给状态机（核心取舍）

- **流程推进（阶段跳转、回退）**→ 状态机确定性控制：业务流程不能有概率性
- **意图识别入口、自由文本理解** → 模型判断：自然语言入口需要弹性
- **结构化数据展示** → 数据库取事实：模型不得编造
- **一句话原则**：模型负责"理解输入、组织表达"，状态机负责"流程正确"，数据库负责"事实正确"

**局限提示**：教程的状态机 SessionContext 存内存 Map，重启丢失——与第四章 InMemory 同款问题，生产化需落库（可复用第五章 messages/conversations 模式）。

## 五、前端组件渲染层

### 5.1 ComponentRenderer 的关键设计

- **映射层**：根据 type 分发到对应 React 组件（switch-case / Record 映射），协议新增类型 → 加一个映射分支
- **单向数据流**：后端产出 UIResponse → 前端渲染 → 用户操作产出 UIAction → 回传后端，前端不做流程判断
- **组件无状态**：每个组件只负责渲染和收集操作，不保存跨轮状态（状态在后端 collectedData）
- **统一回调**：所有组件通过 `onAction(UIAction)` 回传，容器层统一处理
- **未知类型 Fallback**：遇到不认识的 type 不崩溃，降级为提示文案——协议演进的容错底线

### 5.2 容器层职责

聊天容器管理消息历史（message + components），区分两条输入路径：文本输入走 `/chat`，UI 操作走 `/action`，UI 操作在聊天流里以 `[UI 操作: selection → select]` 形式留痕，保持对话可读。

## 六、流式适配：text streaming + component batching

### 6.1 天然矛盾与折中方案

结构化组件与流式输出存在本质冲突：**Markdown 文字可以逐 Token 到达，但组件必须拿到完整 JSON 才能渲染**（半截 form/selection 既不能展示也不能交互）。

折中方案：**文字流式输出、组件整包下发**。

### 6.2 关键设计取舍表

| 维度 | 设计决策 | 理由 |
|---|---|---|
| JSON Agent（抽取/澄清） | 不流式，静默收集 | 中间 JSON 不可读不可解析，推送反而制造混乱 |
| Markdown Agent（分析/汇总） | 逐 Token 流式 | 即时反馈，显著降低感知延迟 |
| UI 组件 | 整包批量渲染 | 组件需要完整数据才能工作 |
| 进度通知 | 独立事件流（progress 消息） | 单独驱动进度条，不混在正文里 |
| 持久化时机 | 流结束后一次性落库 | 避免半截数据污染数据库，减少写入次数 |

### 6.3 流式架构的六个改造点（演进路线）

1. **流式协议信封**：统一 StreamMessage（messageType: markdown / ui / progress / done / error），一个 SSE 连接混传多种消息类型，前端按 messageType 分发
2. **后端编排区分 Agent 类型**：JSON Agent 静默累积不 yield；Markdown Agent 逐 Token yield；agent_start/agent_end 事件驱动进度
3. **SSE 长连接**：`flushHeaders()` 毫秒级建立连接，消灭 30 秒黑盒等待
4. **前端状态分离**：`streamingMessage` 与已完成 `messages` 解耦，每个 Token 只重渲染正在流的那条消息，不触发整个列表重渲染
5. **类型动态切换**：Markdown 阶段 → UI 阶段无缝过渡
6. **交互状态记录**：`interactionState` 记录已提交操作、自动禁用对应组件，防重复提交

### 6.4 优化前后体验对比

| 阶段 | 一次性返回 | 分段流式 |
|---|---|---|
| 0~5 秒 | 黑盒等待 | 进度条 0%，"提取中…" |
| 5~15 秒 | 继续等待 | 进度 40%，Markdown 逐字输出 |
| 15~30 秒 | 继续等待 | 80%→100%，组件整包渲染可交互 |
| 用户感受 | 卡住了？要等多久？ | 看得到进度、内容，能马上操作 |

## 七、工程化生产清单

上线前必须补齐的四件事：

1. **协议版本管理**：AIUIResponse 加 `version` 字段，前端按版本做兼容渲染，未知版本 fallback 纯文本
2. **未知组件降级**：default 分支兜底提示，永不崩溃
3. **后处理校验层**：过滤空选项 selection / 空字段 form、message 兜底、组件数量截断
4. **防重复提交**：interactionState 记录已操作组件并禁用，保障数据一致性

## 八、三个判断框架（本章最有复用价值的部分）

### ① 什么时候该让模型返回 UI 组件？——用「用户是否需要操作」判断

- 需要**做选择**（选类型/维度/下一步）→ 组件
- 需要**补信息**（填表单/确认参数）→ 组件
- 需要**降低理解成本**（把"读一大段话自己总结"改成可点可提交）→ 组件
- 反例：解释说明、开放问答、闲聊——纯文本更自然

### ② 什么时候用 text streaming + component batching？——用「内容是否支持增量渲染」判断

- Markdown/分析说明 → 天然适合逐 Token 流式
- 表单/选择器/确认框/表格 → 必须等完整 JSON 整包渲染
- 进度信息 → 独立事件流
- 如果连组件都想边生成边出现 → 当前协议不够用了，需要设计增量 UI 协议

### ③ 什么时候把交互做成协议而不是写死页面？——用「变化频率 vs 复用范围」判断

- 交互流程**频繁变化**（今天 selection→form，明天 card+buttons）→ 协议化
- 同一套能力要被**多端复用**（Web/桌面/移动/不同团队壳层）→ 协议化
- 希望"返回什么组件、如何推进"由模型和上下文共同决定，而非每加分支就改前端 → 协议化
- 反例：长期稳定、几乎不变的简单表单页 → 直接写死更省心

## 九、企业场景扩展

这套"模型输出 UI 协议 → 前端渲染 → 操作结构化回传"的模式在企业内部工具中有极高适配度：

| 教程场景 | 企业落地映射 |
|---|---|
| 需求分析四阶段（选类型→填详情→确认→结果） | 双预防 CRM 的隐患上报流程：选隐患类型 → 填隐患详情表单 → 确认提交 → 整改进度 steps 展示 |
| selection 组件选择分析维度 | 巡查系统里"选择检查表/风险分区/法规依据类别" |
| card + action_buttons 组合 | 法规检索结果卡片 + "查看原文 / 引用到报告 / 相关条款"按钮 |
| steps 进度条 | 多 Agent 法规分析流水线（提取→检索→比对→汇总）的进度可视化 |
| LLM 不得编造数据 | 法规条文、条款编号必须来自法规库检索结果，模型只组织表达——安全生产场景对事实准确性零容忍 |
| 状态机 vs 模型分界 | 上报/整改等合规流程走状态机保确定性；自然语言查询入口走模型理解 |

**可写入简历的表述方向**：设计过 AI 驱动 UI 的前后端协议（8 类组件 + 操作回传契约），用 Structured Output + Zod 约束模型输出，交互流程走确定性状态机、降级兜底保证可用性；实现 text streaming + component batching 的流式策略平衡即时反馈与组件完整性。

## 十、速查清单（复习用）

1. AI 驱动 UI 的本质：**把自然语言理解从交互回路中剔除，换成确定性协议**
2. 协议五原则：type 唯一标识 / 组件自包含 / 操作可回传 / 可组合 / 向后兼容
3. AIUIResponse 三层：**message（必填兜底） + components[] + context**
4. `z.discriminatedUnion` 基于 type 精确匹配，优于 `z.union`
5. **Schema 约束格式，不约束判断** → Prompt 指引 + 后处理校验双层防护
6. **事实从数据库来，模型只负责组织表达**——防幻觉的分界线
7. 双通道：**流程归状态机，理解归模型，事实归数据库**
8. LLM 输出校验失败 → **降级到确定性状态机**，不暴露 500
9. 流式折中：**文字流着走、组件整包发、进度独立事件流**
10. JSON Agent 静默、Markdown Agent 流式、**流结束一次性落库**
11. 前端状态分离：streamingMessage 与 messages 解耦防全列表重渲染
12. 三个判断框架：**需要操作→组件；支持增量→流式；频繁变化/多端复用→协议化**
