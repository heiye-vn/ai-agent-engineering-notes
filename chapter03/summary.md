# 第三章教程总结：LangChain 起手——搭建第一条服务端能力链路

> 来源：《AI Agents 开发实践》第三章（feat/first-chain 分支）
> 核心命题：当一次简单模型调用不够用时，如何把它整理成**可维护、可复用、可测试**的能力链路
> 贯穿任务：从需求文本抽取结构化字段 `action / constraints / entities`，最终收束为 `POST /requirement/extract`

---

## 一、五层递进架构总览

```
模型层(3.4)   → invoke / stream / batch + 统一模型工厂
提示层(3.5)   → ChatPromptTemplate 模板化，告别字符串拼接
链式层(3.6)   → pipe() 串联 模板→模型→解析 成固定流程
解析层(3.7)   → Zod schema + withStructuredOutput，输出可程序消费
工具层(3.8)   → bindTools + ToolMessage 闭环，模型决策、工具执行
收束层(3.9)   → RequirementService + 统一业务入口 + 可测试
```

## 二、逐层知识点

### 1. 为什么引入 LangChain（3.1）

直接用 OpenAI SDK 只解决"能不能调通"，进入业务系统后问题变成"能不能长期维护"：

| 工程问题 | 对应层次 |
|---|---|
| 提示词散落多文件、变量拼接难维护 | 提示层 |
| 结果要作为接口返回值/下游输入，格式必须稳定 | 解析层（结构化输出） |
| 模型只能生成内容，无法调用外部系统/覆盖最新知识 | 工具层/检索层 |
| 单步调用扩展为多步固定流程 | 链式编排（pipe） |

**任务定义先于技术选型**：先把"边界、粒度、结果唯一性、测试断言"定义清楚（如 action 必须唯一、constraints 只留明确约束、entities 只取真实名词），否则后面无法稳定实现。

### 2. 服务端承载的分工原则（3.2）

- `clients/chat-web`：只负责输入、展示、交互
- `services/chat`：组织模型调用、工具、检索、链路
- `packages/contracts`：沉淀跨端复用的共享定义（如 Zod schema）

**为什么复杂度放后端**：API Key 不暴露、工具/检索统一管理、日志/限流/缓存/重试/监控好收口、后续加多模型路由/RAG/MCP/Agent Runtime 有明确落点。

**Next vs Nest**：Next 偏应用层（渲染、RSC、BFF）；Nest 偏服务层（DI、模块化、守卫拦截器、业务编排）。AI 服务压力来自长耗时请求、流式连接、重试超时、工具检索串联，且需要独立扩容/告警/超时策略——Nest 更适合做长期 AI 能力底座。

### 3. 配置分层（3.3）

| 类型 | 位置 | 内容 |
|---|---|---|
| 环境变量 | `.env`（开发）/ Docker Compose 注入（生产） | 密钥、令牌、外部服务地址 |
| YAML | `config/langchain.yaml` | 模型参数、功能开关、检索配置 |
| 代码 | `prompts/` 目录 | 提示模板、业务逻辑 |

- 配置加载器 `loadLangChainConfig()`（js-yaml 读 YAML）+ `getApiKeys()`（读 env）
- **铁律：凡令牌/密钥/服务地址一律走 `process.env`，不写进 YAML、不写进代码；`.env` 必须进 `.gitignore`**

### 4. 模型层：统一工厂 + 三种调用（3.4）

- **统一模型工厂 `createChatModel()`**：从 YAML 读模型参数、从 env 读密钥/baseURL，Service 里不直接 `new ChatOpenAI`——初始化收口，换模型只改一处。

| 方式 | 语义 | 适用场景 | 注意点 |
|---|---|---|---|
| `invoke()` | 单次完整结果 | 接口型能力（默认选择）；主链路先跑通；便于重试/超时/缓存/幂等治理 | 长内容会拉长用户等待 |
| `stream()` | 边生成边返回 | 前端逐字渲染、降低体感延迟；实时日志透出；支持断连中断 | 难做结构化消费与断言测试 |
| `batch()` | 一批输入并行跑 | 离线任务、数据回填、评测回归测试 | 失败处理更精细：顺序对应、部分失败重试、单条超时影响整体 |

- 流式路由要点（SSE）：`Content-Type: text/event-stream` + `Cache-Control: no-cache` + `Connection: keep-alive`，`for await` 逐 chunk `res.write()`。
- 消息构造：`SystemMessage`（角色设定）+ `HumanMessage`（用户输入）组成 `BaseMessage[]`。

### 5. 提示层：模板化（3.5）

- 字符串拼接的局限：提示重复、改动分散、变量插入不直观。
- 做法：`prompts/requirement.prompt.ts` 导出 `REQUIREMENT_SYSTEM_PROMPT`（角色+严格规则：不编造、action 唯一、constraints 只留"必须/至少/不得/不能"、entities 只取真实名词、缺失返回空数组）和 `REQUIREMENT_USER_TEMPLATE`（含 `{input}` 占位符）。
- `ChatPromptTemplate.fromMessages([['system', ...], ['human', ...]])` 组装可复用提示。
- **先渲染后调用**：`promptPreview` 只用 `prompt.invoke({ input })` 渲染验证变量替换，不调模型；确认无误再 `formatMessages({ input })` 转消息数组送模型。

### 6. 链式层：LCEL 与 pipe()（3.6）

```ts
const requirementChain = requirementPrompt
  .pipe(model)
  .pipe(new StringOutputParser()); // 输出统一转纯字符串
```

- 链本身同样支持 `invoke / stream / batch` 三种执行方式。
- **上链时机判断：同一"prompt + model + parser"组合出现两次以上，就该收成链**——此时你维护的已不是某次调用，而是一条业务流程。
- 工程思路：**业务流程与返回方式分离**——先写成 chain，再按产品需要选 invoke 还是 stream。
- 典型场景：需求抽取接口、文案标准化改写、分类打标（chain.invoke）；长文本生成、前端即时反馈（chain.stream）；历史数据回填、导入预处理、评测回归、定时任务（chain.batch）。

### 7. 解析层：结构化输出（3.7）

- 自由文本的局限：只要结果要作为接口返回值、下游输入或测试断言，不稳定就是问题。
- Schema 定义在共享包 `@autix/contracts`（前后端共用类型）：

```ts
export const RequirementResultSchema = z.object({
  action: z.string().describe('唯一核心动作'),
  constraints: z.array(z.string()).describe('明确约束条件'),
  entities: z.array(z.string()).describe('关键实体'),
});
export type RequirementResult = z.infer<typeof RequirementResultSchema>;
```

- `model.withStructuredOutput(RequirementResultSchema)`：让模型直接按 schema 输出，返回即结构化对象，不靠后置字符串清洗。
- **兜底策略**：仍可能出现输出夹杂解释文本——需提示约束（明确要求 JSON）+ 解析兜底 + 测试样例三管齐下。
- 工程价值：只有结构稳定，测试、回归、复用和下游编排才有基础。

### 8. 工具层：调用闭环（3.8）

- **工具本质**：`tool(fn, { name, description, schema })`——可调用函数，zod schema 声明参数，description 供模型理解何时调用。
- **分工原则：模型负责决策（是否调、调哪个、何时继续），工具负责给出确定性结果。**
- 完整闭环四步：

```
模型声明(tool_calls: 工具名+参数+调用id)
  → 系统执行(targetTool.invoke(toolCall.args))
  → ToolMessage 回填({ tool_call_id, content: JSON.stringify(结果) })
  → 再 invoke 生成最终答复
```

- `bindTools([toolA, toolB])` 把工具绑定到模型；用 `toolMap`（name → tool）做分发。
- **ToolMessage 必须带 `tool_call_id`** 关联到具体哪次调用。
- 四类适用场景：规则校验（抽取后验约束）、事实查询（查库/查配置）、流程编排（模型路由+工具执行）、高风险闭环（可审计、可限权、可定位失败点）。
- **判断标准：答案依赖外部事实/外部规则/真实动作 → 上工具；否则优先 prompt / 结构化输出。**

### 9. 收束层：统一业务入口（3.9）

- Service 按业务域命名（`RequirementService`），不用 `SummaryService` 这类泛化技术演示命名。
- 统一入口 `POST /requirement/extract`，替代一堆演示性路由。
- **前端职责边界三件事**：输入需求文本（只采集不预处理）、请求统一接口（不关心背后是哪个模型/链/工具）、展示结构化 JSON（不做二次解析校验）。前端越薄，后端能力迭代联动改动越少。
- 测试要点（`requirement.spec.ts`）：
  - 真实模型调用用 `RUN_LLM_E2E=1` 环境变量显式开启，默认 skip；
  - **断言只验证结构化约定（字段类型、数组非空）+ 关键语义命中（如结果含"手机号"），不锁死具体字符串**——因为模型措辞会随温度波动，这正是 `withStructuredOutput` 要保证与不保证的边界。

### 10. 五条判断标准（3.10 小结精华）

| 问题 | 判断标准 |
|---|---|
| 何时上模板？ | 同一段提示出现在 2+ 处，或改一次提示要动多个文件 |
| 何时上链？ | "模板→模型→解析"已稳定且被多接口/任务反复调用 |
| 何时上结构化输出？ | 结果要进程序（接口返回值/下游输入/测试断言），不只是给人看 |
| 何时上工具？ | 答案依赖外部事实/规则/真实动作，模型自身生成覆盖不了 |
| 何时收束？ | 示例验证通过后，要变成可被其他模块/团队/环境稳定调用的入口 |

- 后续衔接：**RAG** 解决知识覆盖不足（先检索再回答）、**MCP** 解决能力边界封闭（标准化协议接外部系统）、**Agent Runtime** 解决流程不灵活（动态决定下一步）。
- 不变的核心原则：**先定义任务 → 再把能力放到正确的层 → 最后收束成可测试、可迭代的入口。**

## 三、面试题（含答案）

### Q1：什么情况下需要引入 LangChain，直接用 OpenAI SDK 不行吗？

**答**：单次简单调用 SDK 完全够用。但当出现四类工程问题时就该引入 LangChain：① 提示词变多且散落多处，需要模板化管理；② 模型输出要进入程序（接口返回值、下游输入），需要结构化输出保障；③ 需要工具调用与检索增强，模型自身只能生成内容；④ 多步骤形成固定流程，需要可组合、可复用、可测试的编排。LangChain 的价值不是换种写法调模型，而是把提示、模型、解析、工具、编排放进同一套编程模型，提前收口这些迟早出现的工程问题。

### Q2：`invoke()`、`stream()`、`batch()` 分别适合什么场景？

**答**：
- `invoke()`：默认选择，一次拿到完整结果。适合接口型能力、链路早期跑通主流程、需要做重试/超时/缓存/幂等治理（请求边界清晰）的场景。
- `stream()`：边生成边返回，适合前端逐字渲染降低体感延迟、长文本生成、实时日志透出、需要支持用户中断（断开连接即停止）的场景。注意流式难做结构化消费与断言测试——要稳定 JSON 时先 invoke 拿结构化结果，再决定是否把解释性内容做成流式。
- `batch()`：一套逻辑跑多条输入，适合离线任务、数据回填、评测回归测试。注意失败处理更精细：返回顺序对应、部分失败重试、单条超时对整体的影响。

### Q3：为什么 AI 能力建议放 Nest 服务端而不是 Next/BFF 层？

**答**：① 安全边界：API Key、向量库凭证集中后端，最小暴露、易审计限权；② 治理收口：长耗时请求、流式连接、重试超时、工具检索串联这些 AI 特有压力，在 Nest 的模块化 + DI + 守卫/拦截器体系里更容易统一治理（日志、限流、缓存、监控）；③ 部署节奏：后端能力迭代与前端发布解耦，需要独立扩容、独立告警、独立超时策略；④ 演进落点：多模型路由、RAG、MCP、Agent Runtime 都是服务端形态。Next 定位是前端应用层 + BFF，做贴近 UI 的数据获取；Nest 才是长期承载 AI 能力的后端底座。

### Q4：LLM 应用的配置应该怎么分层管理？

**答**：两层分离——**敏感且随环境变化的**（密钥、令牌、外部服务地址）走环境变量：开发放 `.env`（进 `.gitignore`），生产由 Docker Compose / secrets 注入，不落盘；**不敏感但频繁调整的运行时策略**（模型参数、temperature、功能开关、检索 topK）放 YAML 配置文件，可读可调。再配一个统一加载器收口。原则是"安全相关的变化"和"运行时策略的变化"分开处理，密钥永不进代码和 YAML。

### Q5：`ChatPromptTemplate` 相比直接拼字符串有什么优势？

**答**：① 角色结构显式化：system 与 human 从一开始就分开，符合模型的对话协议；② 变量填充标准化：`{input}` 占位符由模板引擎填充，避免手写拼接出错；③ 可复用可测试：模板是独立常量，可以先渲染验证（`prompt.invoke()` 看渲染结果）再送模型，把"提示是否正确"和"模型是否正常"两个问题解耦；④ 集中管理：提示收进 `prompts/` 目录，修改不再牵一发动全身，也为后续接入链式编排（pipe）提供标准接口。

### Q6：LCEL 的 `pipe()` 是什么？什么时候该把调用收成链？

**答**：`pipe()` 把"提示模板 → 模型 → 输出解析"等多个 Runnable 串成一条固定流水线，链本身仍保留 `invoke / stream / batch` 接口。**判断标准：同一"prompt + model + parser"组合出现两次以上就该收成链**——从那时起维护对象从"某次调用"变成"一条业务流程"。链的收益：一处组装多处调用、整体可替换可测试、业务流程与返回方式分离（先写成 chain，再按需选 invoke 或 stream）。典型场景：需求抽取接口、文案标准化、分类打标；批量场景如历史数据回填、评测回归。

### Q7：`withStructuredOutput()` 的原理和工程价值？输出仍不稳定怎么办？

**答**：它基于 Zod schema 让模型按固定结构输出（底层走模型的 JSON mode / function calling 能力），返回直接是符合 schema 的对象，省去后置字符串清洗。工程价值：结果可断言、可进下游、可做回归测试——这是 LLM 应用从 demo 走向工程的前提。若仍出现输出夹杂解释文本，三管齐下：① 提示层明确要求只返回 JSON、不输出解释；② 解析层加 JSON 提取/校验兜底；③ 测试层准备多样例覆盖。注意 schema 定义放共享包（如 `@autix/contracts`），让前后端消费同一份类型。

### Q8：描述一次完整的工具调用闭环流程。

**答**：四步——① **声明**：`bindTools()` 绑定工具后 invoke，模型返回 `tool_calls` 数组（含工具名、参数、调用 id），此时模型不直接给最终答案；② **执行**：服务端按 `toolMap[toolCall.name]` 找到工具，`targetTool.invoke(toolCall.args)` 执行，拿到确定性结果；③ **回填**：把结果包装成 `ToolMessage`，**必须带 `tool_call_id`** 关联到具体调用，push 回消息列表；④ **再生成**：带着工具结果的完整消息列表再次 invoke，模型生成最终答复。关键理解：模型负责决策（是否调、调哪个、何时继续），工具负责确定性结果；这条闭环可审计、可限权、可定位失败点，是后续 RAG、MCP、Agent 的基础范式。

### Q9：为什么工具结果要用 `ToolMessage` 回填，而不是拼进 HumanMessage？

**答**：`ToolMessage` 通过 `tool_call_id` 与模型声明的调用一一对应，模型能明确知道"这段内容是我那次工具调用的结果"，从而正确区分自身推理、用户输入和外部事实。拼进 HumanMessage 会让模型把工具结果误认为用户说的话，可能导致误解或被注入攻击（工具返回的内容被当作用户指令）。同时结构化的消息类型让整条执行流程可审计——每个环节（谁声明、谁执行、结果归谁）都有明确归属，排查失败点时能精确定位。

### Q10：对依赖真实模型调用的接口，测试断言应该怎么设计？

**答**：① **显式开关**：真实调用耗时且依赖外部服务，用环境变量（如 `RUN_LLM_E2E=1`）控制，默认 skip，CI 按需开启；② **只断言结构化约定**：字段类型（string/array）、非空约束——这是 `withStructuredOutput` 能保证的部分；③ **语义命中而非字符串相等**：如结果 JSON 序列化后 `toContain('手机号')`，因为模型措辞会随温度/版本波动，锁死具体字符串必然 flaky；④ **设置合理超时**（如 30s）。核心思路：明确"结构化输出保证什么、不保证什么"，断言落在这条边界上。

## 四、一句话总结

LangChain 起手式的精髓不是记住 API，而是掌握**分层递进的能力建设方法**：先定义清楚任务 → 逐层叠加（模型→模板→链→结构化→工具）→ 收束成统一业务入口。每层都有一条明确的"何时上"判断标准，复杂度始终有归属，系统就不会退回"到处散落、难以维护"的状态。
