# 第五章教程总结：从 Mock 到生成——数据库设计与向量化落库

> 来源：《AI Agents 开发实践》第五章（feat/db-vector 分支）
> 核心命题：能力验证型 demo 如何升级为**可持久、可隔离、可观测**的生产级系统
> 主线：数据库建模 → 会话持久化 → 文件上传 → 解析分块 → 向量化落库 → 任务通知 → 端到端链路
> 本章不含实现细节，只梳理知识点、选型对比与实践原则

---

## 一、Demo 与生产的差距：三类核心问题

第四章完成了 Memory / Tools / Embeddings / Multi-Agent 的能力验证，但数据停留在进程内存和本地文件。判断一个 demo 是否需要"生产化改造"，看三个信号：

| 问题 | Demo 形态表现 | 生产要求 | 改造方向 |
|---|---|---|---|
| **数据不持久** | `InMemoryChatMessageHistory` 重启丢失、`MemoryVectorStore` 进程退出清空 | 长期运行、历史回溯、知识库复用 | PostgreSQL + Prisma 持久化 |
| **用户不隔离** | 无身份概念，所有请求共享同一上下文 | 多用户服务、数据私有 | JWT 鉴权 + userId 贯穿所有表 |
| **文件不可管理** | `workspace/*.json` 手写 mock，无元数据、无权限、无生命周期 | 用户动态上传、按人隔离、可检索 | 文件上传 + 元数据入库 + 向量化 Pipeline |

**实践原则**：学习验证阶段用内存实现完全合理——关键是上层接口不要绑死底层实现（第四章"存储可替换、接口不变"的抽象在此兑现），生产化时只换存储层，链路代码零改动。

## 二、系统架构：四个关键环节

整条生产链路可拆为：

1. **用户鉴权**：复用已有 RBAC 用户系统，JWT 识别用户（跨服务共用 `JWT_SECRET`）
2. **文档管理**：上传 → 解析 → 分块 → 向量化 → 落库，建立用户私有知识库
3. **会话对话**：创建会话 → 发消息 → 加载历史 → 语义检索 → Multi-Agent 分析 → 结果持久化
4. **统一存储**：会话、消息、文档元数据、向量全部落在同一个 PostgreSQL 实例

**微服务边界的实践原则**：chat 服务不内建 User 表，`userId` 用裸 String 关联、不建跨服务外键——用户系统归 user-system 维护，跨服务外键会造成迁移耦合与数据一致性灾难。

## 三、向量存储选型：pgvector vs 独立向量数据库

本章最核心的选型决策：

| 维度 | MemoryVectorStore | **pgvector（本章选择）** | Qdrant / Milvus 等专用向量库 |
|---|---|---|---|
| 定位 | 开发/原型验证 | 中小规模生产 | 大规模生产 |
| 部署成本 | 零 | 零额外服务（复用现有 PG） | 需独立部署运维一套服务 |
| 数据一致性 | 无 | 与业务表同库，**事务一致性好** | 跨库，需处理双写一致性 |
| 规模上限 | 进程内存 | 百万级向量以内 | 亿级、分布式 |
| 运维复杂度 | 无 | 低（跟随 PG） | 高（独立监控、扩容、调参） |

**实践原则**：
- 教学/中小规模业务选 pgvector 的本质理由是**不额外引入独立服务**——会话、消息、元数据、向量统一在一个库里，一条 SQL 里 JOIN 业务表就能做权限过滤。
- **规模到百万级再评估专用库**。只要上层检索接口保持稳定（`similaritySearch(query, userId, topK)` 这类抽象），底层存储可在后续无痛替换。
- 这与第四章"MemoryVectorStore 只是临时形态"的铺垫一脉相承：先跑通接口语义，再替换实现。

## 四、数据库设计：五张核心表与关键决策

### 4.1 数据模型全景

| 表 | 职责 | 关键字段设计 |
|---|---|---|
| `conversations` | 会话容器，绑定 userId | `@@index([userId])` 支撑用户会话列表查询 |
| `messages` | 会话内每条消息 | `role` 枚举（USER/ASSISTANT），与 LangChain 消息类型映射对齐；`metadata` JSON 存附加信息 |
| `documents` | 上传文件元数据 | `status` 跟踪处理进度（pending → processing → done/error）；`chunkCount` 冗余计数 |
| `document_chunks` | 分块文本 + 向量 | `embedding` 类型 `vector`；`chunkIndex` 保序 |
| `task_events` | 异步任务事件 | 既支撑 SSE 实时推送，也作为可查询的任务历史（含 `readAt` 已读标记） |

### 4.2 值得记住的设计决策（面试高频）

| 决策 | 理由 | 通用原则 |
|---|---|---|
| `messages` / `document_chunks` 用 `onDelete: Cascade` | 删会话同步清消息、删文档同步清分块，避免孤儿数据 | **从属数据随主体级联删除** |
| `documents.status` 用字符串而非枚举 | 处理状态取值会随业务扩展（如新增 archived） | **取值稳定的用枚举求类型安全，易变的用字符串求灵活** |
| `embedding` 标记为可选（`?`） | 分块创建与向量化是异步两步，chunk 可能先落库后补向量 | **异步流水线的中间态要允许为空**，检索时 `IS NOT NULL` 过滤 |
| schema 层不限向量维度 | 当前写 384 维（本地 embedding 模型），换 OpenAI 1536 维无需改表 | 维度由 embedding 模型决定，切换模型时保证写入一致即可 |
| Prisma 不原生写 `vector` 类型，用 raw SQL | ORM 对扩展类型的支持滞后 | **ORM 覆盖不到的能力用 raw SQL 补，不必为此弃用 ORM** |

## 五、会话持久化：换存储不换接口

第四章的 `Map<string, InMemoryChatMessageHistory>` 替换为数据库实现，核心知识点：

- **自定义 ChatMessageHistory 只需实现 `getMessages()` / `addMessage()` 两个契约**，底层从内存换成 Prisma，`RunnableWithMessageHistory` 的用法完全不变。
- **role 映射规则**：`HumanMessage → USER`，其余（AIMessage 等）→ `ASSISTANT`。
- **权限校验下沉到服务层**：`findById(conversationId, userId)` 内部校验归属，查不到 404、不属己 403——隔离逻辑不能依赖前端自觉。

**验收方法论**：持久化改造的验收标准不是"接口能通"，而是**"重启服务后历史完整保留 + 跨用户访问返回 403"**——前者验证持久、后者验证隔离，缺一不可。

## 六、文件上传与管理

知识点集中在工程约束清单：

- **类型白名单**：TXT / MD / PDF / DOCX，MIME 校验放在 fileFilter 层拦截
- **大小限制**：10MB 上限
- **目录隔离**：`uploads/{userId}/` 按用户分目录，文件名加时间戳防冲突
- **元数据先行**：上传即写 `documents` 表（status: pending），物理文件与数据库记录一一对应
- **异步处理模式**：`POST /:id/process` 校验归属后触发后台处理，**立即返回 202 Accepted**——耗时任务不占用请求连接，进度通过通知机制感知（见第八节）

**实践原则**：上传与处理必须解耦。同步处理大文件会拖垮 HTTP 连接池；202 + 异步 + 事件通知是文件处理类任务的标准形态。

## 七、解析、分块与向量化 Pipeline

### 7.1 解析层：工厂模式按 MIME 路由

不同格式解析成本差异大（PDF/DOCX 需专用解析库，纯文本直接读），**工厂按 MIME 分发到对应 parser**，新增格式只加一个 parser + 一行路由，不动主流程。

### 7.2 分块策略

- `RecursiveCharacterTextSplitter`：递归按分隔符切分，尽量在自然语义边界断开
- **chunkSize: 500 / chunkOverlap: 50**：500 字符适配中文短文档；50 字符重叠避免语义在切分边界断裂
- **重复处理幂等**：重新处理文档前先清空旧分块（deleteMany），保证多次触发结果一致

**选型认知**：chunk 大小是检索质量与上下文成本的权衡——块太大召回粗糙且撑 prompt，块太小语义碎片化；重叠 10% 左右是社区常见起点，需按语料实测调优。

### 7.3 向量化与检索

- **向量生成**：本地 embedding 模型（384 维），mean pooling + L2 单位化——单位化后余弦相似度与内积等价
- **pgvector 距离运算符**：`<=>` 余弦距离（值越小越相似，`1 - distance` 转相似度分）；另有 `<->` L2 距离、`<#>` 内积
- **用户隔离检索**：检索 SQL JOIN documents 表按 `userId` 过滤——**隔离不是可选项，是检索语句的一部分**
- **生产数据原则**：向量字面量需内联 SQL（pgvector 不支持参数绑定 vector），但 userId / topK 等必须参数化，防注入

**异步两步落库**：先批量生成向量，再逐条写入 chunk 并 UPDATE embedding 字段，最后更新文档 status 与 chunkCount——**状态机推进（pending → processing → done/error）让失败可观测、重试有依据**。

## 八、异步任务通知：SSE 推送

### 8.1 SSE vs WebSocket 选型

| 维度 | SSE | WebSocket |
|---|---|---|
| 通信方向 | 服务端 → 客户端（**单向**） | 双向 |
| 协议 | 标准 HTTP，**浏览器自动重连** | 独立协议，需手动处理重连 |
| 复杂度 | 低 | 高，网关/Nginx 需额外配置 |
| 适用场景 | **任务进度、状态通知** | 聊天、实时协作 |

**判断原则**：只需要服务端推、客户端不需要实时上行 → SSE。本章场景（向量化任务进度通知）是典型的单向通知。

### 8.2 事件机制的关键设计

- **先落库、再推送**：emit 时事件先持久化到 `task_events`，推送失败不影响记录留存；用户离线期间的错过的消息可通过 `GET /api/tasks/history` 补查——**实时推送是体验优化，持久化才是可靠性保障**
- **连接管理**：`Map<userId, Set<Response>>`，一个用户多 Tab 共用；心跳（30s）防中间层断连；连接关闭时清理
- **生命周期管理**：定时清理离线连接 entry；定期归档删除 30 天前的事件，防止表无限膨胀

### 8.3 单实例的局限与演进路径

内存 Map 维护 SSE 连接**只在单进程内有效**。多实例部署时，推送层演进为 **Redis Pub/Sub**：任意实例收到事件发布到频道，持有该用户连接的实例负责推送。事件本身已落库，历史查询不受影响。

**实践原则**：这是典型的"先单机简单实现、留好演进路径"——连接管理与事件持久化分离，让扩容时只需替换连接层。

## 九、端到端链路串联

最终闭环：**登录 → 创建会话 → 上传文档 → 触发处理 → 带知识库上下文的分析 → 结果入库**。

与第四章的关键差异对照（这张表是整章的浓缩）：

| 环节 | 第四章（Mock） | 第五章（生产） |
|---|---|---|
| 会话历史 | InMemoryChatMessageHistory（内存 Map） | DbChatHistory + PostgreSQL |
| 文档检索 | 手动灌库到 MemoryVectorStore | 用户上传 → 自动向量化 → pgvector 语义检索 |
| 用户隔离 | 无，全局共享 | JWT 鉴权 + userId 过滤 |
| 结果持久化 | 写本地 md 文件 | messages 表，关联会话与用户 |
| 重启后状态 | 全部丢失 | 完整保留 |

**容错细节**：检索失败或无文档时，链路降级为"无文档上下文分析"继续执行，而不是整体报错——**知识库是增强项，不是依赖项**。

## 十、企业场景扩展：安全生产法规 RAG 的映射

这套"上传 → 分块 → 向量化 → 带隔离检索"的架构可直接映射到双预防 CRM 的法规检索知识库场景：

| 教程概念 | 法规检索场景落地 |
|---|---|
| documents / document_chunks | 法规原文（PDF/DOCX）入库，按条款自然段落分块 |
| userId 隔离检索 | 质控/巡查/质研人员只见授权范围内的法规库（如按企业、按行业分类隔离） |
| 202 + SSE 任务通知 | 批量导入新法规时异步建库，导入进度实时可见 |
| 检索失败降级 | 法规库未覆盖时退化为普通问答，并提示"未检索到相关条款" |
| status 状态机 | 法规入库失败可定位、可重试，避免半成品库污染检索结果 |

**可写入简历的表述方向**：设计过"文档解析 → 分块 → 向量化 → pgvector 持久化 → 带权限过滤的语义检索"完整 Pipeline，支持异步处理与任务事件通知，多用户数据完全隔离。

## 十一、速查清单（复习用）

1. demo → 生产的三个信号：**数据不持久、用户不隔离、文件不可管理**
2. pgvector 选中理由：**不引入独立服务 + 同库事务一致性**；百万级再上专用库
3. 微服务边界：**跨服务 ID 用裸 String，不建外键**
4. 级联删除：从属数据随主体 Cascade
5. 枚举 vs 字符串：**取值稳定用枚举，易扩展用字符串**
6. 异步两步落库：**embedding 允许为空，检索时过滤 NULL**
7. 分块参数起点：**chunkSize 500 / overlap 50（约 10%），按语料实测调优**
8. 距离运算符：`<=>` 余弦距离，`1 - distance` 转相似度
9. 文件处理标准形态：**202 + 异步 Pipeline + 事件通知**
10. SSE 事件机制：**先落库再推送**；离线补查走历史接口
11. 多实例演进：SSE 连接管理 → **Redis Pub/Sub**
12. 知识库定位：**增强项而非依赖项**，检索失败要能降级
