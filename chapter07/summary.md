# 第七章教程总结：Agent 推理的三层决策机制——路由、执行与优化

> 来源：《AI Agents 开发实践》第七章
> 核心命题：当任务不再是一条固定 Pipeline 时，Agent 应该如何决定下一步做什么？
> 主线：固定编排的边界 → 路径级推理 → 三层决策机制（路由 / 执行 / 优化）→ 按层组合 → LangGraph 承接
> 本章不含实现代码，只梳理知识点、选型对比与实践原则；实现放到第八、九章

---

## 一、从固定编排到动态推理

### 1.1 第六章链路的本质：固定编排 + 局部推理

第六章的五段式流水线（提取 → 澄清 → 分析 → 风险 → 汇总）**不是"没有推理"**，而是两件事同时存在：

- **编排固定（Static Orchestration）**：节点、边、执行顺序在开发期写死，每次执行路径完全一致
- **局部推理（Local Reasoning）**：每个节点内部都在做判断（extractAgent 抽字段、analysisAgent 多维度评估）

**关键认知**：推理一直存在，只是过去只发生在节点内部；本章要讨论的是如何让推理进一步发生在**节点之间**。

**固定编排的优势与边界**：

| 优势 | 边界（四个"不能"） |
|---|---|
| 可预测：路径固定，调试测试简单 | 不能跳步：简单需求仍机械走完全流程 |
| 可控制：不会出现模型擅自跳步 | 不能回退：某步结果不理想无法自动重做 |
| 可视化：天然映射 steps 进度条 | 不能分支：无法按中间结果临时改路径 |
| —— | 不能自检：结果自相矛盾不会被自动发现 |

适用判断：**流程稳定、输入结构清晰、异常可预期** → Fixed Workflow 依然是最优解。

### 1.2 动态推理：路径级决策

当"编排本身"需要运行时决定，就进入动态推理。核心循环四动作：

```
观察 Observe → 决策 Decide → 行动 Act → 再观察 Observe → ...
```

与传统架构最关键的区别：**"决策"这一步不再由开发者编码写死，而由模型在运行时参与决定**。这种能力叫 **路径级推理（Path-level Reasoning）**——本章所有讨论的总纲。

触发场景举例：多条需求一次输入（步骤数随需求条数变化）、输入混杂多种需求类型（要先识别类型再选链路）、分析中发现外部依赖（临时插入新 Agent）、报告前后矛盾（需要自检修订）。

### 1.3 三层决策机制：本章核心框架

常见误区：把 ReAct、Plan-and-Execute、Reflexion 当作"三选一"的同级替代关系。真相是**按层组合**——三者分属不同层级：

| 层级 | 回答的问题 | 典型策略 | 输入 → 输出 | 类比 |
|---|---|---|---|---|
| **路由层 Routing** | 任务该进入哪条链路？ | Router / Classifier | 任务特征 → 目标链路 | 分诊台 |
| **执行层 Execution** | 链内每一步如何推进？ | ReAct / Plan-and-Execute / Fixed Workflow | 目标 + 当前状态 → 下一步动作 | 科室诊疗 |
| **优化层 Optimization** | 结果够不够好？要不要修？ | Reflexion / Critic-Refine / Self-Consistency | 执行结果 → 修订后结果 | 复核医生 |

三层关系是**递进而非并列**：路由在最外层送任务进链，执行层在中间推进任务，优化层在后段复核修订。

**最重要的一点**：第六章的 Fixed Workflow 没有被淘汰，而是被**重新定位为执行层的稳定实现方式**，与 ReAct、Plan-and-Execute 是"同层不同策略"。生产系统中 Routing 的下游往往接的就是一条或多条 Fixed Workflow。

## 二、路由层 Routing：先决定走哪条链

### 2.1 是什么

Routing 是动态推理体系的**入口层**，解决的问题：系统里同时存在多种任务类型、多条专门化链路时，如何按输入特征把任务分发到最合适的处理路径。

- Router 通常是一个**轻量分类 Agent**：输入任务描述，输出标签（如 functional / performance / security），系统按标签分发
- Routing 只关心"任务应该去哪"，不负责"进入以后怎么做"——**这一层选错，后面执行再精细结果也偏题**

### 2.2 适合场景的三个特征

1. 存在**多种任务类型**（功能 / 性能 / 安全 / UI-UX 需求）
2. 已经有**多条专门化链路**（不同分析维度、不同专家提示词、不同工具集合）
3. 归类**主要依赖文本特征**，不需要先做复杂多步推理

强行用一条统一 Workflow 覆盖所有类型会出现两类问题：某些步骤对某些任务无效（给功能需求做威胁建模）、关键维度被遗漏（性能需求没做容量规划）。

### 2.3 与 Fixed Workflow 的关系（六、七章的连接点）

> **Routing 的本质，就是"动态选择某一条固定 Workflow"。**

- Fixed Workflow 是 Routing 下游的**稳定处理单元**
- 第七章没有推翻第六章，而是在外层**补一层动态选路能力**
- 每条 Workflow 内部依旧可以沿用局部推理模式

对后续章节的意义：第八章 Router 只是图中的一个节点，下游连接多条子图（子图本身可以是 Fixed Workflow）；第九章 Multi-Agent 的第一步往往也是先 Router 分派，再进入各自执行链。

📌 **Router 是最容易被低估的一层**：很多人学完 ReAct 就想"所有任务上 ReAct"，但生产系统里大量任务只需要 Router 输出标签 + 下游稳定 Workflow。核心原则——**"动态"不等于"每一步都自由"，而是"只在需要动态的那一层动态"**。

## 三、执行层 Execution：任务在链内如何推进

执行层两种典型策略：ReAct 与 Plan-and-Execute。核心区别不在"哪个更高级"，而在**决策是局部做，还是先全局做**。

### 3.1 ReAct：边想边做

来自 2022 年同名论文，核心思想：**让模型在每一步先显式表达思考，再决定行动**。

```
Thought → Action → Observation → Thought → ...（循环直到 Final Answer）
```

- 与普通工具调用的区别：普通调用中"决定调哪个工具"是隐式的；ReAct 把这一步思考**显式化**
- 三要素：Thought（为什么这样做）、Action（做什么、调什么工具传什么参）、Observation（拿到什么新信息）

💡 你每天都在用 ReAct：ChatGPT / Claude 联网搜索时显示"正在搜索……"本质上就是 Thought + Action，模型读取结果继续推就是 Observation → Thought。

**特点**：决策粒度细（每步只决定下一步）、灵活性高（随中间结果调整方向）、可观测性强（思考链可追踪调试）。

**最适合的场景**：
- 步骤通常 3–5 步以内
- 中间结果会明显影响下一步选择
- 工具数量有限（< 10 个）且用途清晰
- 需要追踪推理过程

反例：第六章的标准五段式流程本身稳定，用 Fixed Workflow 更可靠高效；但"模糊需求，需要动态判断先查相似、先估复杂度还是先澄清"，ReAct 优势立刻显现。

### 3.2 Plan-and-Execute：先规划，再执行

"先画地图，再按图前进"，明确拆成两个角色：

- **Planner（规划器）**：接收任务，一次性产出完整计划（步骤、内容、依赖关系）
- **Executor（执行器）**：按计划逐步执行，不再重新思考下一步

**实用优势**：规划和执行可以用不同能力层级的模型——规划用强模型（需要全局推理），执行用便宜的小模型或函数节点（只是调工具读结果做简单判断），**显著降本**。

**Replan 机制**：执行失败不是"边做边猜"，而是把"已完成什么、什么失败了、剩余什么"重新交给 Planner 生成新计划。触发条件：工具调用失败、中间结果显示原计划不成立、步数/成本超预期。工程要点：**Replan 必须拿到"已完成状态"，否则 Planner 会重复规划做过的事**——这正是 LangGraph 共享 State 天然擅长的事。

**最适合的场景**：
- 步骤较多（5–15 步）的复杂任务
- 步骤依赖关系明确、整体结构稳定
- 对 Token 成本敏感
- 需要向用户展示"可确认的执行计划"（Planner 的 plan 可直接映射 UI 的 `steps` 组件，配合 `confirmation` 让用户执行前审批——相对 ReAct 的天然优势：中间产物就是结构化计划）

### 3.3 本质区别：局部决策 vs. 全局规划

| 维度 | ReAct（局部决策） | Plan-and-Execute（全局规划） |
|---|---|---|
| 决策时机 | 每一步都重新决策 | 任务开始时先完成整体规划 |
| 决策视野 | 只关注当前状态和下一步 | 关注整个任务的全局结构 |
| 模型成本 | 大模型往往每步参与 | 规划用大模型，执行可降级小模型/函数节点 |
| 中间调整 | 天然支持，自动根据观察变化 | 需要显式触发 Replan |
| 适合任务 | 中间结果高度影响后续动作 | 步骤依赖清晰、整体结构稳定 |
| 类比 | 游客在每个路口都重新看地图 | 出发前规划整条路线再按图前进 |

**一句话选型标准**：问自己——这个任务的下一步，是否必须看到上一步的具体结果才能决定？
- **是** → ReAct
- **否** → Plan-and-Execute（若流程固定且很短，Fixed Workflow 已足够）

注意：两者都**只解决执行层问题**，不回答"该走哪条链"（路由层），也不回答"结果够不够好"（优化层）。

## 四、优化层 Optimization：结果生成后如何自我修正

执行层策略的共同局限：**负责推进，但默认不回头看**——输出有误、遗漏条件、前后矛盾，系统自己不会主动发现。优化层补上这一环，类比软件开发中的 **Code Review + 自动化测试 + 修订重跑**。

三类策略共同点：**都不负责推进任务，只负责评估和修正结果**——这是与执行层最根本的区别。

### 4.1 Reflexion：做完之后整体评估

在执行链路**末端**增加自我评估闭环，三个角色：

- **Actor**：真正执行任务的 Agent（可以是 Fixed Workflow / ReAct / Plan-and-Execute）
- **Evaluator**：整体评估结果，给通过/不通过或打分——扮演"通读全文"的角色（每个节点只看自己那段，没人站在全文视角检查，Evaluator 补的就是这个）
- **Reflector**：评估不通过时，提炼失败原因，形成可操作的修正建议，反馈给 Actor 重跑

⚠️ **Reflexion 不是"又一种执行方式"**：它不推进任务，只是包裹在已有执行器外侧的优化机制，因此**可以叠加在 ReAct / Plan-and-Execute / Fixed Workflow 之上**，不冲突。

日常可观察的手动版 Reflexion：第一轮让模型整理会议纪要 → 人工指出漏了行动项和责任人 → 第二轮明显更好。把"人工指出问题"换成"Evaluator 自动发现"，就是 Reflexion。

**最适合的场景**：输出质量有明确标准（可写进 prompt/规则）、允许更长响应时间（离线报告、后台任务）、输出是长文本/报告/复杂代码等"一次往往做不对"的内容。类比：**Agent 世界里的自动化测试 + 自动修复**。

### 4.2 Critic-Refine：局部修订，不整链重跑

Reflexion 整条链重跑成本高；只修局部问题就用 Critic-Refine——Critic 指出问题，Refine 只修订有问题的局部内容（如只改"排期建议"那一段，不重跑前面的提取分析）。

| 维度 | Reflexion | Critic-Refine |
|---|---|---|
| 评估对象 | 整体结果 + 整条执行过程 | 主要关注最终产出 |
| 修订方式 | 带着反思重跑整条链 | 只修订有问题的局部内容 |
| 成本 | 较高 | 较低 |
| 适用场景 | 执行过程本身可能出错 | 执行过程可信，结果表达仍需打磨 |

**优先选 Critic-Refine 的场景**：产出是长文本/报告/代码，问题集中在结构措辞完整性；中间步骤整体可信，问题只在"最后一公里"；成本敏感；需要多轮细修但不想每次从头开始。

### 4.3 Self-Consistency：多次推理再投票

思路不同：既不评估整链也不局部重写，而是**让模型独立推理多次，对结果投票或聚合**。利用的特性：对存在相对明确答案的判断类任务，多次独立推理的多数结果比单次输出更稳定。

**适合**：分类判断（功能/性能需求）、风险评级（P0/P1/P2）、复杂度评估（高/中/低）、冲突判定（是否冲突）——跑 3–5 次取多数。

**不适合**：开放式生成（长报告、代码、创意文案）——不存在天然的"多数答案"，强行投票反而稀释表达质量。

### 4.4 优化层选型速查

- 执行链本身可能出错，需要整体回看可能重跑 → **Reflexion**
- 执行过程基本可信，只需修文案/补结构/改表达 → **Critic-Refine**
- 任务是有明确答案的判断题（分类、评级、判定）→ **Self-Consistency**
- 流程稳定、输出无需打磨 → 优化层不是必选项

## 五、模式组合：真实系统如何按层组装

真实系统几乎不会只动一层，标准三段式：**路由 → 执行 → 优化**，每层内部可替换不同策略：

| 组合 | 路由层 | 执行层 | 优化层 | 典型场景 |
|---|---|---|---|---|
| 经典需求分析 | 任务类型 Router | Fixed Workflow（五段式） | Critic-Refine（修报告） | 单条需求分析 + 报告打磨 |
| 模糊需求探索 | — | ReAct | Reflexion | 不确定先调哪个工具时的动态探索 |
| 批量需求评审 | 任务类型 Router | Plan-and-Execute | Critic-Refine（修汇总报告） | 一次评审 50 条需求 + 排期材料 |
| 判断类任务 | — | Fixed Workflow / ReAct | Self-Consistency | 风险评级、冲突判定、优先级打分 |

**三条组合原则**：

1. 不是三选一，而是**三层分别选策略**
2. 某一层可以不用动态机制（只有一条执行链时不需要 Router）
3. **层与层之间职责要清晰**：选路的不负责执行，执行的不负责质检，质检的不替代执行

第六章系统的演进路径（三步）：新增 Router 按需求类型分派 → 每条 Workflow 保持 Fixed 但中间步骤差异化 → 所有链路末端统一接 Critic-Refine 打磨报告，再走已有 UI 协议输出。演进优点：**向后兼容**（不推翻已有 Workflow）、**增量落地**（先补 Router 再补优化层）、**职责清晰**（新增需求类型 = 加一条 Workflow + Router 加一个分支）、**天然适配 LangGraph**。

## 六、LangGraph：三层决策的落地结构

概念上 if-else + while 也能讲清三层决策，但生产环境会撞上一系列工程问题，这正是 LangGraph 系统性解决的：

**六大工程问题**：状态管理（分类结果/推进状态/重试轮次放哪维护）、持久化与恢复（长任务中途重启如何续跑）、并行执行（无依赖步骤如何安全并发）、条件分支（分类结果如何驱动路径）、人工介入（需要确认时如何暂停等待恢复）、流式反馈（状态变化如何实时推前端）。

LangGraph 把推理过程建模为**有状态的图（Stateful Graph）**：Node（决策/执行单元）、Edge（转移关系，固定边或条件边）、State（全图共享的上下文）。

**三层决策 → LangGraph 的自然映射**：

| 层级 | 策略 | LangGraph 表达 |
|---|---|---|
| 路由层 | Router / Classifier | Router Node + 条件边（Conditional Edge） |
| 执行层 | Fixed Workflow | 固定边串联的子图（Subgraph） |
| 执行层 | ReAct | Agent Node + Tool Node 之间的循环边 |
| 执行层 | Plan-and-Execute | Planner Node → Executor 子图，条件边触发 Replan |
| 优化层 | Reflexion | Evaluator Node 判断通过与否，不通过回到 Reflector / Actor |
| 优化层 | Critic-Refine | 主链后串联 Critic Node → Refine Node |
| 优化层 | Self-Consistency | 同一节点的并行分支 + Aggregator Node |

映射"自然"的原因：LangGraph 原生提供这些能力——节点执行后状态自动持久化（断点恢复）、条件边承载 Router 分类结果、并行分支适配 Self-Consistency 与独立步骤、`interrupt` 机制支持任意节点暂停等人工确认（对接第六章 `confirmation` 组件）、流式回调把节点级过程实时推前端（对接 SSE 与 `ThinkingIndicator`）。

**章节衔接**：第七章建立三层认知框架 → 第八章用 LangGraph 逐一落地（Router Node、ReAct Agent、条件路由、并行、持久化）→ 第九章组合成生产级 Multi-Agent 系统，与 UI 协议、流式渲染合流。

## 七、复习速查：五个核心决策问题

| 问题 | 判断标准 |
|---|---|
| **何时从固定编排切到动态推理？** | 任务类型多样化需进不同链路 / 中间结果会改路径 / 结果需系统自检修订。编排稳定结果可信 → 继续用 Fixed Workflow 更可靠高效 |
| **何时引入路由层？** | 已有多条专门化 Workflow / 归类靠文本特征即可 / 各链路 Agent 组合、工具、提示词差异明显。只有一条执行链 → Router 只是开销 |
| **执行层 ReAct vs Plan-and-Execute？** | 下一步高度依赖上一步结果 → ReAct；步骤结构可提前规划 → Plan-and-Execute；流程固定且短 → Fixed Workflow 足够 |
| **优化层三种怎么选？** | 链路本身可能出错 → Reflexion；过程可信只修表达 → Critic-Refine；有明确答案的判断题 → Self-Consistency；无需打磨 → 可以不要优化层 |
| **何时迁移到 LangGraph？** | 需要状态持久化/断点恢复、条件分支、并行、Replan、人工确认、流式反馈。一次性脚本/短链路 Demo/无状态任务 → 手写流程更直接 |

**一句话总结**：动态推理 = 路径级决策；ReAct / Plan-and-Execute / Fixed Workflow / Reflexion / Critic-Refine / Self-Consistency 不是互相替代的"模式"，而是分属路由、执行、优化三层的**可组合策略**——"只在需要动态的那一层动态"。
