# 《第一章：把模型变成能力》知识点总结

> [!NOTE]
>
> 核心命题：把大模型从“会说话的黑盒”变成“可被系统使用的模块”。模型调用是一切 Agent 能力（工作流、工具调用、RAG、多 Agent）的地基——地基不稳，上层只会放大混乱。

## 1. 智能体底座——模型调用

- 工具调用、任务编排、RAG 都是模型调用**之上的扩展**，不是起点
- 输入不清、输出不稳会被工作流放大错误、被工具链扩散偏差
- 工程目标不是“偶尔答得好”，而是**可约束、可复用、可验证**

---

## 2. 调用 = 一次受约束的对话

五层调用结构（缺一不可）：

| 层               | 作用                                    | 缺失后果                   |
| :--------------- | :-------------------------------------- | -------------------------- |
| **system**       | 全局角色、规则、行为边界、输出风格      | 模型行为容易漂移           |
| **task**         | 本次调用要完成的目标                    | 目标会模糊                 |
| **context**      | 补充业务背景、代码片段、文档等必要信息  | 结果容易失真               |
| **format**       | 输出结构约束（如 JSON、字段、代码格式） | 输出难以消费，比如无法解析 |
| **post-process** | 对结果进行解析、校验、兜底、重试、记录  | 系统缺少闭环，导致错误扩散 |

- 三种消息角色：**system**（长期稳定约束）/ **user**（本次任务）/ **assistant**（历史回复，维持多轮连续性）
- 关键区分：**user 管“这一次做什么”，system 管“以后每一次怎么做”**——别把角色、任务、格式全揉进 user
- 输出的三层含义：内容层（逻辑对不对）、结构层（格式对不对）、**消费层**（程序能否稳定接住）

---

## 3.Prompt = 轻量级行为契约

本质类似传统开发中的“函数签名 + 参数约束 + 返回结构”。五个控制手段：

1. **角色设定**：稳定分析视角，不是让模型“演得像”
2. **任务定义**：任务模糊 → 输出开放；越明确越稳定
3. **上下文补充**：给关键信息而非堆材料——缺上下文 = 模型靠猜
4. **输出约束**：让结果从“能看”变成“能接”
5. **边界限制**：明确“不要做什么”；信息不足时禁止猜测，让系统**安全失败**

---

## 4. 漂移：模型不稳定因素

**五类表现**：结果不一致 / 格式漂移（JSON 夹带解释、漏字段、改字段名）/ 跑题 / 看似合理实则有误 / 保守与过度发挥之间摇摆

| 原因         | 对策                                   |
| :----------- | :------------------------------------- |
| 温度过高     | 工程任务用低温度；**但温度治标不治本** |
| 上下文不足   | 补关键背景，减少猜测                   |
| 任务不清     | 把任务说清楚（第一优先级）             |
| 输出约束不足 | 细化到字段名、类型、嵌套结构           |
| 缺校验机制   | 运行时校验 + 兜底重试                  |

> [!TIP]
>
> 金句：任务本身模糊时，低温度只会让模型“更稳定地模糊”。工程能力 = 把不确定性收束到系统可接受范围内。

---

## 5.结构化输出：让结果能进系统

- 自然语言对人友好，对程序**不可解析**（哪段是模块？哪段是风险？）
- 结构化的本质是**可消费**：summary 可展示、modules 可拆分、risks 可评估、questions 可形成澄清清单
- JSON 是默认选择，但不是唯一：XML / YAML / CSV / **choice-route（分类路由、Agent handoff）** / 固定格式代码、SQL、DSL——**选型看下游消费场景**
- 只说“按 JSON 返回”不够，必须约束：字段名固定、类型明确（数组 vs 字符串）、空值返回空数组而非省略字段
- **异常处理**：预定义失败结构（如 `questions: ["信息不足，无法判断"]`），让系统能识别错误、决定重试或人工介入

---

## 6. 封装：从一次调用到能力模块

从 Demo 到模块的演进路径：

1. 先跑通**最小版本**（业务逻辑/Prompt/参数/解析混在一起不可长期维护）
2. **先定义结果 schema**（`RequirementAnalysis` 接口）——规定系统接收什么结构
3. 统一调用层 `LLMClient`：`generateText` / `generateJSON`，收敛客户端创建、模型选择、JSON 解析
4. Prompt 独立成可维护资源：system 模板常量 + user 构造函数，可版本化
5. 业务模块只关心能力（`RequirementAnalyzer.analyze()`）
6. **校验 + 重试 + 兜底不是附加项**：类型守卫 `isRequirementAnalysis` + `withRetry`
7. 留扩展接口：工具参数、会话状态、日志追踪、模型路由

推荐目录结构：

```sh
src/
  llm/
    client.ts       # 统一调用层
    prompts.ts      # Prompt 资源
    schemas.ts      # 结果类型定义
    validators.ts   # 运行时校验
  services/
    requirementAnalyzer.ts  # 业务能力模块
```

---

## 7. 三个递进示例

需求摘要（Prompt 影响输出粒度）→ JSON 结构化（“可读”→“可消费” + 运行时校验）→ 代码生成（角色 + 任务 + 边界约束直接决定生成代码的可运行性与边界完整性）

---

## 总结

用 system/task/context/format 分层收束不确定性 → 结构化输出让“人能懂”变“系统能处理” → post-process 校验兜底形成闭环 → 最终封装成可复用、可扩展的能力模块。
